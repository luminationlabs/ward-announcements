# Architecture

## Stack

- **TypeScript** (ESM) on **two runtimes**: Cloudflare Workers (`src/worker.ts`, the deployment target, and `src/host.ts`, many wards on one deployment) and Node (`src/server.ts`, for local development, the tests and the Docker image). See [Three entry points, one app](#three-entry-points-one-app) and [The many-ward host](#the-many-ward-host).
- **Hono** for routing and middleware — runtime-agnostic, which is what lets the same `app.ts` serve both. On Node it is bound to a socket by `@hono/node-server` (whose `serveStatic` handles `public/`); on Workers the runtime hands it `fetch` directly and static files come from the assets binding.
- **SQLite** behind a small driver seam (`sqldriver.ts`): `better-sqlite3` on Node (`driver-sqlite.ts`, file-backed), Cloudflare **D1** on Workers (`driver-d1.ts`), and a ward's own **Durable Object SQLite** on the many-ward host (`driver-do.ts`). `db.ts` holds only SQL and knows neither — which is why every query uses positional `?` parameters and every atomic write goes through `batch()`, the two things D1 constrains.
- **markdown-it** renders announcement and program bodies to sanitized HTML (`html: false`). Two configured instances: both understand [centered lines](#centered-lines), and programs additionally understand [dot-leader rows](#dot-leader-rows).
- **Uploaded images** go through a second seam (`filestore.ts`): a directory on disk under Node (`filestore-fs.ts`), a **Cloudflare R2** bucket on Workers (`filestore-r2.ts`) or, when no bucket is bound, the database itself (`filestore-sql.ts`). See [Image attachments](#image-attachments).
- **@block65/webcrypto-web-push** builds the RFC 8291 payload and RFC 8292 VAPID header with WebCrypto only; `push.ts` does the `fetch` itself. Needing only WebCrypto and `fetch` is what lets the same push code run on both runtimes. Payloads use the Declarative Web Push format.
- **croner** runs the weekly schedule on Node (and the daily program-retention sweep). Workers has no croner: a per-minute cron trigger asks the same shared arithmetic (`schedule-core.ts`) whether the last occurrence has been covered, and on the many-ward host each ward's Durable Object alarm runs the same tick (`tick.ts`).
- Server-rendered HTML (admin) + static HTML/vanilla JS (public) — no frontend framework.

## Three entry points, one app

`app.ts` — every route, the access gate, the admin UI — is identical everywhere. Only the entry point differs, and it owns everything a runtime does differently:

| | Node (`server.ts`) | Cloudflare Workers (`worker.ts`) | Many-ward host (`host.ts`, per ward) |
|---|---|---|---|
| **Boot** | Once, at process start: config, driver, schema, shell | Lazily on first use, memoised per isolate, in two halves — core (config, driver, schema) for any invocation, the app shell only for a request | In the ward's Durable Object constructor, under `blockConcurrencyWhile`, migrations and seeding in one storage transaction |
| **Storage** | `createSqliteDriver(DATABASE_PATH)` | `createD1Driver(env.DB)` | `createDurableObjectDriver(ctx.storage)` |
| **Images** | `createFsFileStore(uploadsPath)` (`IMAGE_STORE=database`: `createSqlFileStore()`) | `env.IMAGES ? createR2FileStore(env.IMAGES) : createSqlFileStore()` | `withPrefix(createR2FileStore(env.IMAGES), '<object id>/')`, else `createSqlFileStore()` |
| **Static files** | `serveStatic` over `public/` | The `ASSETS` binding, with `run_worker_first` so the gate sees every request first | The front door serves shipped static files itself; everything else goes to the ward's object |
| **Config** | `process.env` (+ `dotenv`) | The `env` argument's string-valued entries (vars + secrets) | The same, plus the ward's stored address; no owner password unless `WARD_OWNER_SIGNIN=on` |
| **Sending** | Enqueue, then drain to empty inside the request | Enqueue, drain one chunk, leave the rest to the cron trigger | Enqueue, then drain to empty inside the request (Workers Paid) |
| **Schedule** | A croner job, rebuilt when the admin changes the time, with a per-minute job asking `uncoveredSlot()` behind it | A per-minute cron trigger asking `uncoveredSlot()` | The ward's own alarm, set to `nextWake()`; an hourly cron pokes every ward |
| **Program retention** | Swept at boot and by a daily croner job | Swept from the per-minute tick, guarded to once a day | Swept from the alarm's tick, guarded to once a day |

Three consequences worth knowing:

- **A Workers boot failure is caught, not fatal.** `worker.ts` answers `/healthz` *before* booting anything, so the health check never depends on the config, D1 or the shell assets; a genuine boot failure is logged and returns a plain 503 rather than Cloudflare's opaque 1101 on every route with nothing in the log. `public/icons/` is generated and git-ignored (as is `public/vendor/pdfmake/`, which only the dashboard's Save as PDF button ever fetches), so `/icons/ios-splash.html` is read as **optional**: otherwise a bare `wrangler deploy`, a CI job that skips `npm run assets`, or a dashboard rollback would take the whole Worker down over a missing decoration.
- **Rate limiting is per-isolate on Workers.** `ratelimit.ts` counts in memory and Cloudflare may run many isolates at once, so the limits blunt password guessing rather than metering an API. A genuinely global limit would need Durable Objects or Cloudflare's rate-limiting binding. The member-facing routes (`/api/access`, `/api/subscribe`) allow 300 a minute per IP and `/api/invite` 60, because the launch ritual is a chapel full of people on one wifi address doing the same thing in the same minute — a cap of twenty would tell the twenty-first member that a link they had just been handed was expired. The gate page also tells a 429 apart from a rejected code: it says people are joining, forgets that the code was "tried", and retries after a jittered few seconds (pinned in `test/gate-unlock.test.js`).
- **`worker.ts` deliberately does not import `@cloudflare/workers-types`.** Those types are ambient globals and would redefine `Buffer`/`fetch` project-wide, breaking every Node-side module; the handful of bindings it uses are declared structurally instead, so one `tsconfig.json` checks both.

## The many-ward host

`src/host.ts` serves any number of wards from one Worker, each in a SQLite Durable Object of its own. How to deploy and run it is DEPLOYMENT.md [§ 2b](./DEPLOYMENT.md#2b-hosting-many-wards-one-deployment); this is how it is built.

- **The front door** (the module's default export) answers `/healthz` before anything else, and hands `/__operator/…` on any hostname, and every path on `OPERATOR_HOST`, to the operator app. Any other request is looked up by hostname in `RegistryDO` — one object (`idFromName('registry')`) that knows which wards exist and which hostname each answers on — through a per-isolate cache that keeps each answer for 60 seconds (`WARD_CACHE_MS`), so an ordinary request costs no registry call. The cache is bounded (1,000 entries, the oldest dropped first) because the wildcard route lets anyone make up hostnames. When the registry cannot be reached, an expired entry is used rather than taking a known ward down; with none, the reply is a 503. An unknown hostname is a 404 that wakes nothing, a suspended ward a 503. Shipped static files are served from the front door; everything else goes to the ward's `WardDO`, which is named by the ward's **id**, never its hostname, so a ward can move address and keep its data.
- **One ward** is the ordinary `createApp()` against its own database (`driver-do.ts`), run inside a `Tenant` of its own (`tenant.ts`). Objects of one class can share an isolate, so `host.ts` calls `requireTenantContext()` first: per-ward state lives in `tenantLocal()` slots, and code that runs outside a ward throws rather than reading another ward's. Boot — migrations, seeding, the access code, the schedule defaults — is one storage transaction under `blockConcurrencyWhile`, so a failed migration leaves the ward as it was. A suspended ward's object also refuses public requests itself (503), because other isolates' caches may still call it active for up to a minute; the operator's calls still reach it, so it can be exported or resumed.
- **Scheduled work** is the ward's own alarm, not a per-minute cron: `alarm()` runs `runTick(now, files, logger, 'all')` from `tick.ts` — the same tick as the single-ward Worker, but draining the whole queue, since the host is on Workers Paid — and sets the alarm to `nextWake()`: the next scheduled send, the next claimable queue row, now for a send left pending, and never more than six hours away (the daily housekeeping and a backstop). It is derived, never stored, and re-derived after every write request, so a saved meeting time or a new skip can never leave a stale alarm. An hourly cron (`0 * * * *`) pokes every active ward, which boots it (running any pending migrations) and sets an alarm if one went missing. A suspended or deleted ward clears its alarm.
- **Sign-in.** The platform password is the host's `ADMIN_PASSWORD`: the operator's API token and the operator page's password. The page allows five sign-in attempts a minute; the API, which answers on every ward's hostname, allows five *wrong* passwords a minute (`failureLimit` in `ratelimit.ts`), after which an address is refused whatever it sends — the right password too, or a right guess would get through — and correct requests are never counted. Shorter than 16 characters (`MIN_PLATFORM_PASSWORD` in `operator.ts`) it is refused outright, with an error in the log: no operator and no owner sign-in until a long one is set. A hosted ward has **no owner sign-in** unless `WARD_OWNER_SIGNIN=on` (only the test configs set it), so its sign-in page offers passkeys alone; the operator gets into a ward by minting an admin invite for themselves, and then appears in its People list. When owner sign-in is on, each ward's owner-session key mixes in the ward's id, so one ward's cookie never opens another.
- **Images** share one R2 bucket, each ward under its own prefix (`<Durable Object id>/<key>`, `withPrefix` in `filestore.ts`), so `/images/<key>` on one ward can never serve another's; with no bucket bound, a ward keeps them in its own `file_chunks`. `IMAGE_QUOTA_MB` caps the image bytes one ward may hold (an upload that would pass it is refused); it is read on any deployment, and unset or 0 means no limit.
- **Logs name the ward.** Every ward logs through the one logger; once a ward knows its identity, its `Tenant` carries a label (`{ ward, host }`, set by `applyIdentity()`) and `log.ts` adds it to every line, so an error in Cloudflare's logs says which ward it came from.
- **A ward's identity is its own.** Each ward is configured from the host's vars *minus* `PUBLIC_ORIGIN`, `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (`wardVars` in `operator.ts`, applied in `WardDO.boot`): its address is `https://<hostname>` from its registry identity (`applyIdentity`), and its VAPID pair is the one `identity.ts` stores in its own database — or the one Import Backup was given. Let through, a host-wide value would apply to every ward: one relying-party id for every ward's passkeys, one key signing every ward's sends while each ward's stored pair (and the import's "keys supplied" report) said otherwise. They are ignored with a warning in the log rather than refused at boot, since a boot error is invisible to the operator and must not take every ward down. `VAPID_SUBJECT` stays host-wide. In development only, `PUBLIC_ORIGIN` is let through: under `wrangler dev` every ward is on `127.0.0.1:<port>`, which gives nothing to derive an address from.
- **Delete and move run alone**, inside `blockConcurrencyWhile` as import does, so no request or alarm interleaves with them. That cannot recall an image upload already on its way to R2 when a delete began, so a delete leaves one alarm a minute later that sweeps the ward's prefix again; a deleted ward's alarm does nothing else. The operator destroys the ward first and removes its registry row second, so a failure between the two leaves a ward that is gone but still listed; `destroy` therefore gets through every guard in `WardDO.fetch` — a tombstoned ward answers `ok` to it again, and it needs no booted app, only the object's storage and the R2 prefix — so deleting again finishes the job instead of leaving the id and hostname reserved for ever.
- **An import that committed but did not restart** (`restartAfterImport`) is retried by the next request *or* the next alarm, so a ward nobody visits does not wait for the hourly poke with its Sunday notification due.

**The operator** (`src/operator.ts`) runs outside every ward and reaches one only through the front door's private channel to its object (`WardDO.internal`); it never reads a ward's database itself. It has two doors to the same actions. The **page**, at the root of `OPERATOR_HOST`, signs in with the platform password (five attempts a minute) into a `SameSite=Strict` session cookie, refuses a POST the browser marks as from elsewhere (`Sec-Fetch-Site` `same-site` or `cross-site`, or an `Origin` naming another host — `SameSite` alone would not do, since every ward is a same-site sibling of the operator's host), and strips the flash's `?msg=` from the address bar once shown. The **API**, `/__operator/…` on any hostname, takes `Authorization: Bearer <password>` and allows 60 requests a minute. With no platform password set (or one under 16 characters) both answer 404, as if they did not exist; otherwise the page shows its sign-in form, and the API answers 404 to a request without the right bearer password. ## The send queue

A send is **enqueued once and delivered in chunks**, because a Worker on the free plan gets ~10 ms of CPU per invocation and one encryption costs 0.6–1.1 ms there (measured on Workers in production), which is why `PUSH_CHUNK_SIZE` defaults to 12.

- `queueSend()` writes a `send_log` row plus a `send_batches` row (running totals, `slot`, status) and fans out to `send_queue` with one `INSERT … SELECT` — one row per (send, subscriber).
- `drainSendQueue()` **claims** a chunk (see below), encrypts and POSTs each one, then commits the outcome as a single atomic `batch()`. Outcomes are `sent` / `gone` (404/410 → delete the subscription) / `failed` / `retry` (network error, timeout, 429, 5xx).
- When the last row for a send goes, the send **settles**: chronically failing subscriptions are pruned (see below), `send_log.recipient_count` is written exactly once, and the dashboard's health banner is set or cleared.
- Node drains in a loop until empty, so `sendToAll()` returns finished totals and the admin UI sees a finished send. Workers drains one chunk per request/tick.

**The claim lease.** A claim is an `UPDATE` that stamps `send_queue.claimed_at` and a per-drain `claim_token` on the oldest unheld rows, followed by a read filtered on that token. Rows held for longer than five minutes are reclaimable. This is what makes overlapping drains safe — a cron tick running alongside the previous one, or a manual send racing the weekly digest, cannot read the same oldest rows and deliver them twice — and what recovers rows orphaned by an isolate killed mid-chunk.

**Attempts are spent at claim time, not at commit time.** `attempts` is incremented by the claiming `UPDATE`, so a drain that dies before committing has still consumed one. That is the bound against a deterministic mid-chunk crash: with `MAX_ATTEMPTS` (8), a row that keeps being claimed by drains that never finish runs out and is counted as failed *without another delivery attempt*, rather than being re-delivered forever. Re-taking a row whose lease ran out costs more than one attempt (`ORPHAN_CLAIM_COST`, 4, in `db.ts`): a chunk commits only once all its deliveries are done, so a drain killed part-way may already have delivered some of its rows, and at one attempt a re-take they would arrive up to eight times. At four, a row gets one more delivery (in case the kill came before it was sent) and is then given up on, and a row given up on this way is counted against the send, not the subscriber — it may well have arrived.

**A retry backs off.** A `retry` outcome (5xx, 429, a timeout, a network error) clears the lease in the commit *and* sets `send_queue.not_before` to `min(60, 2^attempts)` minutes out, computed in SQL from the row's own counter; the claim query skips rows that have not reached it. The eight attempts therefore span roughly three hours (2 + 4 + 8 + 16 + 32 + 60 + 60 minutes) rather than three consecutive cron minutes, which would let a push service that was down for three minutes cost every affected subscriber the week's digest, even though the message's 24-hour TTL would have carried it. The Workers tick asks `sendQueueReady()` (claimable now) rather than the raw depth before draining, so a queue that is entirely backing off does not stop it settling a stale send or housekeeping; the Node runtime has a per-minute croner job (`startRetryDrain`) doing the same, since its inline drain returns as soon as nothing is claimable and `sendToAll`'s `pending` can be non-zero there too. It settles a stale send as well, only while no drain is running in the process — a send's queue can empty without its own drain settling it, since a 404/410 or a prune deletes that subscription's rows from every send.

**Per-subscriber bookkeeping rides in the commit batch.** Success stamps, failure counters and 404/410 deletions are accumulated across the chunk and written as part of the one atomic `batch()`, not one query each. A crash cannot bump a counter for a row it failed to delete — and on Workers a D1 `batch()` is a single subrequest whatever it contains, where a query per subscriber would spend twelve to twenty-four of an allowance of fifty.

**Two guards on the message itself.** The plaintext is size-checked once per send (`MAX_PAYLOAD_BYTES` = 3993, the largest the encryption library accepts): an oversize message fails the whole send immediately, with a log line and a dashboard banner naming the size, instead of throwing per subscriber into a catch that looks exactly like bad key material and would give every member a failure count. And every push `fetch` carries `AbortSignal.timeout(10s)`, so an endpoint that accepts a connection and never answers costs one delivery a retry rather than the cron tick's whole minute (or, on Node, an admin's request hanging until the OS gives up). Every non-delivery is logged with its status code or error class and the endpoint's *origin* — never its path, which is the subscription's credential.

**Pruning.** A subscription that fails a whole send has its `failure_count` incremented; a delivery resets it to 0. At `MAX_FAILURES` (8) consecutive failed sends it is deleted — but *only* when the settling send delivered to somebody, so a systemic problem (bad VAPID keys, a push-service outage) can never wipe the subscriber list in one Sunday. Those removals move from `failed` to `removed` in that send's totals. A settle prunes at most `MAX_PRUNE_PER_SETTLE` (8), in one batch; anything left over is still over the threshold when the next send settles, so a long outage is spread across sends rather than blowing one invocation's subrequest budget.

## Push notification flow

1. Client registers `/sw.js`. On iOS, `PushManager` only exists once the app is **installed to the home screen and launched standalone** — until then we show install instructions.
2. User taps **Enable Notifications** → `Notification.requestPermission()` (must be a user gesture) → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })` using the server's VAPID public key (fetched from `GET /api/vapid-public-key`).
3. Client POSTs the subscription JSON to `POST /api/subscribe`; the server upserts it into `subscriptions` (keyed by unique endpoint). The page re-posts the live subscription at every launch (`syncSubscription`), which is the self-heal for a background rotation that could not reach the server — and is why the dashboard's **Remove** under Subscribers deletes the row *and* blocks the endpoint (`blocked_subscriptions`, a sha256 of the endpoint, one batch; `removeSubscriptionById`). A blocked endpoint, or a rotation whose `oldEndpoint` is blocked (the block then moves to the new endpoint: it was the device that was removed), is answered `409 { blocked: true }` and not stored; the page and the worker then unsubscribe on the device, so the card honestly reads off and the page says the ward removed them. Only the Enable Notifications tap posts `deliberate: true`, which lifts the block in the same batch as the upsert — the launch re-sync and the worker's rotation paths never do. The sender's 404/410 cleanup only deletes the row: that is the push service retiring an endpoint, not an admin's choice. The block list travels in backups like any table (hashes only).
4. To send, the server queues the message for every subscription and drains it in chunks (see [The send queue](#the-send-queue)): each delivery is encrypted with `buildPushPayload()` and POSTed to the subscriber's endpoint. Subscriptions returning **404/410** are deleted (gone); other failures increment `failure_count`.
5. The service worker's `push` handler shows the notification; `notificationclick` focuses an existing app window or opens `url`.
6. **A changed VAPID key is caught on the device.** A subscription is bound to the key it was made with, so after the server's key changes (a restore without the keys, a move to a new host) every push to it is refused, while each visit's re-sync kept resetting `failure_count` and the toggle stayed on. Before re-syncing, the page compares `PushSubscription.options.applicationServerKey` with `/api/vapid-public-key`; on a mismatch it unsubscribes, subscribes with the new key and posts it with `oldEndpoint`. A browser that refuses to subscribe without a tap is left honestly "off" with a "turn notifications on again" message, and the old endpoint is unsubscribed. The worker's `pushsubscriptionchange` / Background Sync path (`ensureSubscription`) makes the same check. A browser that doesn't report the key is assumed current. **Verified on a real iPhone** (iOS 18, installed app): Safari reports the key (a 65-byte `ArrayBuffer`), an unchanged key causes no churn across launches, and after the key was rotated by an Import with supplied keys the app re-subscribed silently — toggle still on, no message — and the next manual send arrived.

> **iOS rule:** every received push must display a user-visible notification, so we always
> `showNotification()` and never use silent pushes.

## Install UX

`install.js` drives an install affordance that's hidden once the app is running standalone (`display-mode: standalone`). It has two shapes, by whether installing is the *required* step:

- **iOS and in-app browsers** — push needs the home-screen app (iOS) or a real browser (a Facebook/Instagram webview), so a dedicated install card leads and the notification card is hidden. Its button opens a bottom-sheet with platform-specific steps, picked by `${platform}-${browser}` plus two version branches: iOS ≤ 18 gets the short Share → Add to Home Screen flow, while **iOS 26+** gets a longer illustrated one, because Add to Home Screen now sits behind a menu — the ••• button at the bottom-right on 26, and on **27** the page menu at the left of the address bar, since 27 turned that bottom-right button into Tabs. Only that first step differs between 26 and 27 (`menuFlow()` supplies the shared share-sheet steps), and the branch reads Safari's `Version/` token: iOS froze the OS token in its UA at `18_6` as of 26, so the OS token would have read 18 forever. Non-Safari iOS browsers are told to open the page in Safari, since iOS web push only works for Safari-installed PWAs. Those steps, and both in-app-browser sets (Safari on iOS, Chrome on Android), lead with a **Copy Link for Safari/Chrome** button rather than "open this page": the credential that unlocked the page was scrubbed from the fragment on arrival and the other browser has its own cookies, so "this page" opened there is the locked gate. The button copies a fresh invite from `POST /api/invite` (the Share sheet's endpoint, so the per-device cap applies), minted as the sheet opens so the tap can still write the clipboard; with no clipboard access the link is shown to copy by hand. iOS 17's `x-safari-https://` scheme would open Safari directly, but it is undocumented and unconfirmed from in-app browsers, so it isn't used.
- **Android/desktop** — push works in the tab, so installing is optional and there is no install card at all: a secondary **Add to Home Screen** button sits inside the notification card, next to Enable/Turn Off, with the Android-only Play Protect note under it. A tap fires the native dialog when the browser offered one (`beforeinstallprompt`), and otherwise opens the sheet with "use the ⋮ menu" steps. That fallback matters on Android: Chrome withholds the event after a WebAPK is uninstalled (often until Chrome is fully restarted) and for months after a dismissed dialog, and a page that only reacted to the event would have no install path at all in those states. So on Android the button shows regardless of the event; on desktop, whose menus vary too much for generic steps, only once the event fires. `test/install-ux.test.js` runs `install.js` in a `vm` to pin this placement per platform.

Instruction images live in `public/img/install/` (simplified SVG depictions — see its README).

## Content freshness & updates

Installed PWAs (especially on iOS) resume a **frozen webview** rather than reloading, and standalone mode has no pull-to-refresh or refresh button — so without help the app could show a stale announcement list, or keep running old code, for days. Two mechanisms in `app.js` handle this, both leaning on the network-first service worker (fresh when online, cached when offline):

- **Stale content:** a throttled `refreshOnResume()` re-fetches **both** `/api/announcements` and `/api/program` (and re-checks the subscribe state) on `visibilitychange`, `focus` and `pageshow`(persisted). Both sections, because the program is the one that is *time*-sensitive: a phone left open through 08:00 on Sunday has to pick the program up without a manual reload. The tab the member is on is left alone — re-running the entry rule under them would swap a section out mid-read. A 30s throttle avoids refetching on quick app-switches, and `refreshOnResume({ force: true })` skips the throttle **and the visibility guard** for the one case where 30 seconds of stale is the wrong answer: the service worker posts `{ type: 'refresh' }` to a window it focused or navigated for a tapped notification, since that path often doesn't reload the page at all (`/` → `/#announcements` is a same-document fragment navigation) and a notification is the strongest signal there is that the content just changed. The visibility guard has to go too, because the worker posts that message *before* calling `focus()` — the page is usually still hidden when it lands, so keeping the guard would drop exactly the refresh that was requested. Note this path is **Android/desktop only**: on iOS 18.4+ a Declarative Web Push notification is rendered and navigated by Safari itself and `notificationclick` never runs, so installed iOS apps fall back to the ordinary throttled resume refresh. That Safari still honours the tab named in the hash is **verified on a real device**: an installed app backgrounded on the Program tab, inside the program window, opened on Announcements when its notification was tapped.
- **Stale code/assets (silent update):** `refreshOnResume()` also calls `registration.update()`, forcing a service-worker update check even when a frozen PWA never navigates. If `/sw.js`'s bytes changed, the new worker installs, calls `skipWaiting()`, and a guarded `controllerchange` listener reloads the page **once** to pick up the new `index.html`/`app.js`/`styles.css`. (The listener is only wired when the page already had a controller, so a first-ever install doesn't reload on launch.) The reload is also **conditional on the page actually being stale**: `index.html` carries the same build id in a `<meta name="build-id">`, and on `controllerchange` the page asks the new controller for its (`{ type: 'build-id' }` over a `MessageChannel`; `sw.js` answers on the port) and reloads only if they differ. Without that, a *cold open* after a deploy — where the network-first worker has already fetched the current shell — would find the new `sw.js`, install it, and reload a page that was already fresh: a second visible flash for nothing. A resumed frozen page whose assets predate the deploy still differs and still reloads. Whenever the page cannot tell (no meta, no reply within 2 s, `postMessage` threw) it reloads, to be safe.
- **Repainting only what changed:** both renderers build the new section into a detached element and swap it in (`swapIfChanged()`) only when its markup differs from what is on screen. The resume refresh runs on every foreground, and rebuilding identical content would re-decode every thumbnail and re-flow the page — another visible blink on reopening the app. The *fetch* is unconditional; only the paint is skipped.

The update chain only fires when **`sw.js`'s bytes change**, so that's made correct-by-construction rather than by-memory: `app.ts` serves `/sw.js` **dynamically** (an explicit route registered ahead of the static handler, like `/index.html`) with a `{{BUILD_ID}}` placeholder in its `CACHE` name substituted for a **content hash of the app-shell assets** (`app.js`, `install.js`, `styles.css`, `sw.js`, plus the rendered `index.html` so an env-only identity change busts too). Any asset change ⇒ new hash ⇒ new `sw.js` bytes ⇒ update. Boot fails fast if the placeholder is missing. There is **no manual cache-version bump**. `/sw.js` and the app shell are served `no-cache` so the browser revalidates them on every update check.

## Dark mode

The member-facing pages — the app shell and the gate page — follow the phone's light/dark setting (`prefers-color-scheme`) by default; members read the program in a dim chapel. An **Appearance** switch at the foot of the app (Auto / Light / Dark) overrides it per device, stored in localStorage under `appearance`. A tiny inline script in both pages' `<head>` (`src/theme.ts`, substituted into `index.html` as `{{THEME_SCRIPT}}`) resolves the choice before first paint — Auto reads the media query, live — and writes the result to `<html data-theme>`, `color-scheme` and the `theme-color` metas; it carries the response's script nonce like every inline script (see Response headers below). It is done with colour tokens: `:root` in `styles.css` defines them, and one rule redefines them for `:root[data-theme="dark"] body:not(.admin)`, so the admin pages, which share the stylesheet and never run the script, stay light. The few things a token can't reach sit in one block at the end of the file: the install illustrations keep a dimmed light plate (they are drawn on white, like iOS's own menus), the share QR keeps a white quiet zone, and the sheet's close glyph is lightened. Both pages carry `<meta name="color-scheme" content="light dark">` and a `theme-color` per scheme. The body stays the header's navy in both schemes, a step deeper in dark, because since iOS 26 the installed app's status bar takes its colour from `<body>` (see the comment at the top of `styles.css`).

The dashboard renders a **QR code** (via `qrcode`) of the access share link when `PUBLIC_ORIGIN` is set, downloadable as **SVG or PNG** — SVG prints sharp at any size, PNG is what a word processor, a slide deck or a text message will accept. The SVG comes from `qrcode`'s own renderer; the PNG cannot, because that path needs `node:zlib` and Workers has none, so [`src/qr-png.ts`](../src/qr-png.ts) encodes the same library's module matrix directly. It is a 1-bit greyscale PNG whose zlib stream is made of *stored* (uncompressed) deflate blocks, which is what lets it skip a compressor entirely: one bit per pixel is a QR's exact representation rather than a compromise, and it keeps a ~1000px download near 130 KB. `test/qr-png.test.js` inflates that stream with `node:zlib` and compares every pixel to the matrix — checking the hand-written blocks against a real implementation instead of against themselves.

Beside the downloads, both roles get a **printable flyer** (`public/flyer-pdf.js`): step-by-step install instructions, iPhone on one side and Android on the other, with the ward's name, home-screen name, QR code and domain filled in — as two half-letter pages, or two copies per letter sheet (each turned a quarter-turn, cut marks at the middle, printed double-sided). It is built in the browser with the same on-demand pdfmake as Save as PDF, but each page is one SVG (svg-to-pdfkit), since an SVG group is the only thing pdfmake can rotate; the copy is wrapped by the script against Roboto's advance widths, and the QR is drawn from the module matrix `/admin/flyer.json` sends, because pdfmake's `qr` node rounds modules to whole points. One pdfmake quirk shapes the fonts: in the browser build an SVG's text can only reach a font pdfmake has already opened, and only by its PostScript name (written up above `registerFonts()`). The address-bar pictures show the registrable domain of `PUBLIC_ORIGIN` (what Safari shows), from a short list of multi-label public suffixes rather than the full Public Suffix List. `test/flyer-pdf.test.js` covers the document, the names and a real pdfmake render on Node; only a browser shows the font quirk, so that was checked in Chrome.

**Admin auth:** `POST /admin/login` compares the submitted password in constant time (SHA-256 + `timingSafeEqual`) and sets a signed, httpOnly session cookie (`cookie-signature` format — `value.` plus a padding-stripped base64 HMAC-SHA256 — with a key mixed from the password-derived `config.sessionSecret`, the database-held `admin_people_secret` and, once bumped, `owner_session_version` (`ownerKey()` in `auth.ts`), so changing the password ends open sessions and a stolen cookie is no offline test of password guesses). Every other `/admin*` route except the sign-in, invite and passkey sign-in routes and `/admin/logout` runs `requireAuth` (or `requireAdmin`, below), which redirects to the login page. The password is the owner's alone; everyone else signs in as a person with a passkey (below). A non-string `password` (a JSON body posting a number, say) is treated as a wrong password rather than reaching `createHash`.

The signed value is **`ok.<issuedAt>`**, and the session check tests that timestamp against the 30-day `MAX_AGE` server-side, because `Max-Age` is a request to the browser, not something a server enforces: without the timestamp a captured cookie would be an admin credential *forever*.

**The owner and people.** The **owner** signs in with `ADMIN_PASSWORD` and is always an admin; their cookie is `pushannounce_session`, signed with `ownerKey()` (above). Everyone else is a **person** (`admin_users`, role `admin` or `editor`) who signs in with a **passkey** (`src/passkeys.ts`, SimpleWebAuthn, verified with WebCrypto on both runtimes). The owner or an admin adds a person and gets a one-time invite link (`/admin/invite#t=…`, a week, the token in the fragment; a new link replaces the old); opening it creates a discoverable passkey (`residentKey: 'required'`), so signing in later needs no username, and user verification is required at both ceremonies (the person unlocks it with Face ID, a fingerprint or a PIN — a security key with no PIN set is asked to make one), and stores its public key in `admin_passkeys`. A person's session is `pushannounce_user`: `u.<id>.<session_version>.<issued>`, signed with `admin_people_secret` (in `settings`, minted insert-if-absent, so changing the owner password signs no one else out). `loadSession` middleware on `/admin` resolves the session once per request and reads the person's row each time, which is what makes **Remove** and **Sign Out Everywhere** (a `session_version` bump) take effect on the next click. Removing one of a person's passkeys bumps it too, in the same batch (`deleteAdminPasskey`): a session does not record which passkey began it, so that is the only way to be sure the device the passkey lived on — a lost phone, usually — is signed out, where it could otherwise enrol a passkey of its own. The browser that removed it is signed straight back in on the new version. A signed-in person can also add a passkey on the device in front of them from **Account** (`/admin/me`, `addOptions`/`addVerify`) — typically a computer they reached with their phone's QR code — so it signs in by itself next time; each passkey is labelled with the kind of device it was made on (`deviceLabel`, from the user agent) so the right one can be removed. Account also lets a person change their own name (`/admin/me/name`), never their role, which only an admin changes under People. No change may leave the ward without an admin who can sign in: removing the only admin with a passkey, making them an editor, or deleting their last passkey is refused (`strandsAdmins` in `app.ts`) until another admin has one, because on a hosted ward the owner password is usually off and that admin is the only way back in. The WebAuthn challenge rides in a five-minute signed cookie (`pushannounce_challenge`, purpose- and invite-bound) instead of server state, except that answering it writes its hash to `spent_challenges` (`takeChallenge`: the insert's own conflict is the check), so a kept cookie cannot answer the same challenge twice — the signature counter, WebAuthn's own replay guard, is 0 for synced passkeys; the daily sweep drops rows past the cookie's five minutes. Signing in either way clears the other kind of session, for the shared clerk's-office computer. The relying-party id is the dashboard's hostname (`PUBLIC_ORIGIN`, else the request's), so passkeys do not survive a change of address — see DEPLOYMENT.md.

An editor may write announcements and sacrament meeting programs (including their images and the Markdown preview), read the send history, hand out the member share link and QR, and **mark a Sunday the weekly notification skips** (`/admin/skips`, see "Sundays that don't send" — the one send-side control they get, because publishing nothing already achieves the same thing). They may delete an announcement but **not a program**: a program is the record of a meeting, a wrong date is fixed by editing, and the retention clock removes old ones on its own, so `/admin/programs/:id/delete` is admin-only and neither the programs card nor the edit page shows an editor the button. Everything else is `requireAdmin`, which 403s a signed-in editor rather than bouncing them to a login they can already pass: `/admin/settings`, `/admin/schedule`, `/admin/meeting-time`, `/admin/weekly-message`, `/admin/send`, `/admin/programs/settings`, `/admin/subscribers` (+ delete), `/admin/backup.json`, `/admin/ward`, `/admin/getting-started/*`, every `/admin/people*` route and every `/admin/access/*` route. (`/admin/me*` is either role: a person's own account.) The dashboard is one view — `dashboardPage` takes the admin-only data as a single optional `admin` bag, and `app.ts` only runs those queries for an admin session — so an editor's page is this page minus those cards, not a second page to keep in step. The route guard is the enforcement; hiding a card only spares an editor a button that would 403. The page is split into three tabs — Content, Notifications, Settings (Sharing, for an editor) — with the same segmented control and hash scheme as the public page, selected client-side so a bookmark or back press keeps its tab. Every admin form is a POST + redirect, and each redirect goes through `dash(tab, msg)` in `app.ts` so it returns to the tab it came from; the flash sits above the tab bar and reads the same whichever tab opens. The program preview (`/admin/programs/:id/preview/fragment`) is deliberately *either* role: the editor is usually whoever typed the names in.

The weekly **schedule** is read for both roles (`schedule` on the dashboard data, beside rather than inside the `admin` bag) even though only an admin can change it. On the Notifications tab its Day and Time row is read-only for both — "Sundays, 9:30 AM", marked *From your meeting time* or *Custom* — and the admin's carries a link to where it is changed (see [The meeting time](#the-meeting-time)); under the card, the editor gets the same two values as a sentence — "goes out with the weekly notification on Sundays at 8:00 AM" — because they are the one publishing what it carries. When auto-send is off that sentence changes rather than gaining a footnote: the wording would otherwise be a plain untruth to someone who cannot see the toggle.

The one card that is deliberately **not** split is the **content policy**, on the Content tab after Programs (`contentPolicyGroup` in `views.ts`): a collapsed `<details>` spelling out what may go in an announcement — no contact details, no private circumstances, care with minors and photos, don't duplicate the ward directory, assume the access link can be passed on. An editor writes the same announcements an admin does, so the rules reach both. It lives in the view rather than in an editable setting on purpose: it is the ward's standing policy, not a per-install preference, and one that can be edited away from the dashboard it governs is not much of a policy.

**Response headers.** The global middleware sets `Referrer-Policy: strict-origin-when-cross-origin`, `X-Robots-Tag: noindex`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and a **Content Security Policy** (`src/csp.ts`) on everything: `script-src 'self' 'nonce-…'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`. A script runs only if it is one of the app's own files or an inline block carrying this response's nonce — fresh per response, held in `AsyncLocalStorage` for the request and stamped by `scriptTag()` — so a value that one day slipped past the escaping in `views.ts` still could not run. The nonce is never computed from the page (hashing whatever scripts a response contains would approve an injected one too), and content stored before the response cannot know it. The member shell is built once and cached, so its one inline script carries a random per-build token that `shellFor()` swaps for the nonce; the build id is hashed from a copy without it, so every isolate still agrees on it. Inline event handlers are refused outright: the dashboard's "Are you sure?" buttons carry `data-confirm="…"`, answered by one listener in the layout — which also closed a hole, since the old `onsubmit` put a person's name, HTML-escaped only, inside a JavaScript string. The CSP includes `form-action 'self'`; the admin layout disables a form's submit buttons once a submit is on its way and re-enables them on `pageshow`. Styles are not restricted. `test/hardening.test.js` (and `test/host/operator.test.js` for the operator page) fails on an inline script without the nonce or any inline handler, and `npm run screenshots` loads every kind of dashboard page in Chrome and fails on anything the policy blocked. **Request bodies are capped** before any route reads them (`bodyLimit`): 1 MB on the dashboard, the largest image plus 1 MB on `/admin/attachments`, 64 KB on the public API. `/api/announcements` and `/api/program` add `Cache-Control: private, no-cache` — both vary by cookie, and the program also varies by wall clock, so a shared cache replaying Sunday's names on Tuesday is exactly the failure the window exists to prevent. Deliberately **not** `no-store`: `public/sw.js` skips caching a `no-store` response (that is how the gate page is kept out of the cache), and the offline copy in a chapel with no usable wifi is the point of the PWA. Everything under `/admin` is the opposite: `private, no-store`, set by a small middleware after the route runs (so a handler with its own directive keeps it), because the service worker registers at root scope and would otherwise keep the dashboard — the live access code, the share link and QR, the subscriber list's endpoints — in Cache Storage on whatever device a clerk used. An unhandled error returns a generic `Internal Server Error` body; the real message goes to the log only.

**Form input is validated, escaped and echoed.** An announcement's `expires_at` must be a real calendar date (`isCalendarDate`, the same check programs use): the public query compares it to today's date as text, so a non-date would sort above every real date and never expire — and the value is rendered, escaped, into the edit form's `value` attribute, where an unescaped interpolation would be a place an editor could plant markup an admin's browser would run. Titles are capped at 200 characters and bodies at 50,000 (`lengthProblem` in `app.ts`) for announcements, pages and programs: generous for anything a ward writes, and small enough that one body can neither slow every member page's render nor outgrow the 100 KB statement `wrangler d1 execute` takes when a backup is restored. A rejected save (missing title, too long, bad date, a program date already taken) re-renders the form from what was **submitted** (`draft` / `draftBody`), not from the stored row, so the page comes back holding what the clerk typed.

**Client IP** (`http.ts#clientIp`, the rate-limit key) depends on what is in front of the app. On Workers it is `cf-connecting-ip`, which Cloudflare sets and a client cannot forge. On Node with `TRUST_PROXY` set it is the **last** element of `X-Forwarded-For`, the address the reverse proxy appended; without it, only the socket address, since every header then comes from the client. Never the leftmost element: proxies *append* the address they observed, so the leftmost is whatever the client sent, and keying on it would let anyone spend a fresh limiter budget per request. Node never reads `cf-connecting-ip`, which a proxy passes through untouched. Each limiter's map sweeps on growth rather than per request, and clears wholesale (with a warning) past 5,000 live entries.

## Announcements & Markdown

Bodies are authored in Markdown and rendered by `markdown.ts` with `html: false` (raw HTML is escaped) and markdown-it's default link validation (blocks `javascript:`/`data:` URLs), so the output is safe to inject as HTML. Links open in a new tab (`rel="noopener noreferrer"`). The public list shows announcements where `published = 1` and (`expires_at IS NULL` or `expires_at
>= today`); the admin sees all, with Live / Hidden / Expired badges. Both honor the manual
`sort_order` (drag-to-reorder in the admin via SortableJS → `POST /admin/announcements/reorder`, which rewrites `sort_order` to 0..n); newly created announcements are inserted at the top.

On the member page an announcement this phone has not shown before carries a small **New** tag. The record is per device — the ids last shown, in localStorage under `seen-announcements`, pruned to what is live — so nothing about what a member has read leaves their phone, and storage that is missing or refuses (private mode, cleared data) just means no tags. A first visit tags nothing. The tags are measured against the ids seen when the *visit* began, not against the record each render rewrites, so the resume and refresh re-renders `app.js` runs while a member is reading never take a tag away; a return after 15 minutes or more away starts a new visit, which matters for an installed iPhone app that resumes for days rather than reloading. `newAnnouncementTags()` is the pure part (`test/new-tags.test.js`). Members never see an announcement's end date — an owner decision — and with nothing live the tab says "No announcements this week."

### The visual editor

Announcements, resource pages and programs are written in one **visual editor** (`editor/`, Tiptap on ProseMirror), mounted over each form's Body textarea. **Markdown stays the format**: it is what the form posts, what the database stores and what members' renderer reads. The editor is a view of it, and the textarea is kept in step on every change.

- **In**: the editor reads Markdown with `editorMarkdownIt()` — the members' own markdown-it instance and rules, typographer off so typed quotes are not saved back curly — through prosemirror-markdown's token-to-node parser. A centered line, a program row and its note, and a blank-line gap therefore reach the editor already recognised by the code that draws them.
- **Out**: prosemirror-markdown's serializer with writers for this schema. Centered paragraphs and headings write `-> … <-`; a row writes `label ... value` and its note `... note`; a line break is a bare newline (the renderer has `breaks: true`); text that merely *looks* like a row, a centered line or a list is escaped so it stays text.
- **Gaps are empty paragraphs.** Each blank line beyond the first above a block (a `gap-N` step) is one empty paragraph in the editor, so pressing Enter twice adds space, as a clerk would expect.
- **Shape is remembered where it is cheap.** Each block records whether it sat on the line directly under the previous one, so rows and the lines under a heading stay stacked; lists keep their tightness and marker (two adjacent lists stay two). A program written in the usual shape (rows on consecutive lines, blank-line gaps) comes back byte-for-byte. A document opened and saved without edits keeps its exact bytes regardless: the textarea is only rewritten after a real change.
- **Program rows** are a node with label, value and optional note cells, drawn with the public page's own `.leader` markup and dots. Typing `Label ... ` (or the `…` an iPhone substitutes) makes one; Enter moves label → value → a new row, and leaves rows on an empty one; Shift+Enter or **+ Note** adds the note.
- **Pasted Markdown** (plain text that looks like it) is parsed rather than pasted literally, so a program written elsewhere and pasted in arrives formatted.
- **Unsaved work is kept on the device.** Every field of the form is stored in localStorage under `ward-draft:<form action>` as it changes (and on `pagehide`), offered back on the next visit if it differs from what the server sent (`editor/drafts.js`). Submitting only marks it submitted; it is cleared when the page the save redirects to carries `?saved=<form action>` (the content routes add it; the admin layout's script, or the editor on an edit page, removes the draft), and every draft on the device is cleared by Log Out, which lands on `/admin/login?out=1` — the flag, not the login page itself, so an expired session keeps them. A save that never arrived — a dropped connection, an expired session, a body too large — leaves it to be offered back, and `requireAuth` sends a signed-out request to `/admin/login?next=<the form>` (`adminReturnPath` in `src/auth.ts` allows only dashboard paths), so signing in again lands where the draft is waiting. A leave-page prompt backs it up where `beforeunload` is honoured; iOS Safari ignores that, so the stored draft is what protects a phone.
- **A new program can start from the latest one**: the New program page links to `/admin/programs/new?from=<id>`, which prefills its text (not its images) as a new, unsaved program.
- **What it cannot hold** — a table, an inline image — makes the parser throw, and that document opens in **Markdown** mode with a note saying why. Anyone can switch to Markdown and back; the choice is remembered per browser.

The editor's content area carries `.editor-preview` inside the forms' `.announcement-editor` / `.program-editor`, so the public stylesheet's body, heading, centering, gap and row rules lay it out exactly as members will see it. It is bundled (≈220 KB gzipped, with markdown-it) by `scripts/vendor-bundles.mjs` and loaded only on the three editor pages; if it fails to load, the plain textarea still works. `test/editor-roundtrip.test.js` holds the round trip in both directions.

## Sacrament meeting programs

The order of a Sunday's sacrament meeting — who presides, conducts, speaks and prays, and which hymns — authored in Markdown by an admin and read on a phone in the chapel. It sits behind the same member gate as the announcements and shares the same image attachments, but differs from an announcement in one way that shapes everything else: **it names people, and it is only meant to be readable while the meeting is happening.**

Rows live in `programs`, one per local date and `UNIQUE` on it — "today's program" has to be unambiguous, and a clerk thinks in dates, not ids. There is no publish flag, no ordering and no expiry column, because none of them decides anything: visibility is entirely the time window below, which is what lets a program be written days ahead without leaking.

### The window, and where it is enforced

`programs.ts` holds the rule, as pure functions over an instant: a day of week, a start time and an end time (`program_window_dow` / `_start` / `_end`, defaulting to Sunday 08:00–14:00), read in `config.timezone` through the same `wallClock`/`dayOfWeek` helpers `schedule-core.ts` uses for cron due-ness — so the window follows local time across a DST change rather than drifting an hour twice a year. The end is exclusive, so "08:00 to 14:00" is shut at 14:00.

**The server enforces it, not the tab UI.** `GET /api/program` returns either

```json
{ "open": true, "date": "…", "closesAt": 1767542400000, "html": "…", "images": [ { "url": "…", "alt": "…" } ] }
```

or, outside the window *and* inside it on a day nobody wrote one,

```json
{ "open": false, "message": "…" }
```

Outside the window the closed reply is deliberately byte-identical whether or not a program has been written, so the response can never be used to probe whether a program exists for a date — only to read one the ward is already meant to be reading. A tab hidden client-side would have left every name one `curl` away; this way the names are not in the response at all.

The message is the clerk's own wording if they wrote one under **Advanced Timing**, and otherwise automatic: "The program will be here Sunday at 8:00 AM." — the window's day of week and start time, no date. Inside the window that sentence would be false, so there it is "Today's program hasn't been posted." `closedProgramMessage()` in `programs.ts` takes only the settings and whether the window is open, never whether a program exists, which is what keeps the guarantee above; inside the window a program's existence is already public, since it is on every phone in the chapel. A blank setting, an unset one and the fixed sentence the setting used to default to all mean "automatic".

A signed-in session gets **no bypass**: the public page shows an admin or editor exactly what a member sees, so what they see is what the ward sees. A bypass would mean the member page never showed a clerk the member view. Proofing a program before its Sunday is the dashboard's job: `GET /admin/programs/:id/preview/fragment` (session) renders the program with the same renderer and the same markup `renderProgram()` in `app.js` builds — the card, the date heading, the body, the thumbnails — and tapping a program's date on the dashboard, or the **Preview** button on its edit page, opens it in a modal, fetched fresh each time.

The service worker caches `/api/program` like any other GET (network-first), so a member who opened the program in the chapel can still read it if the signal drops. That cache is per-browser and only ever holds what that phone legitimately fetched during the window — and it does not outlive the window: an open reply carries `closesAt` (epoch milliseconds, `programWindowClosesAt()`), and offline after that moment the worker deletes its copy and answers closed instead (a copy with no `closesAt`, cached before the field existed, counts as closed). A 401 from any `/api/*` route — the device's access has ended — drops every cached `/api/*` reply too. `test/sw-offline.test.js` runs `sw.js` in a `vm` to pin both.

### Tabs and the entry rule

The public page is one shell with three panels — **Program | Announcements | Resources** — and a segmented control above them. The Resources tab ships `hidden` and `app.js` reveals it once `/api/pages` returns a published page, so a ward that has written none never sees an empty tab; it is never chosen by the entry rule, only by a tap or a `#resources` link. The install and notification cards sit *above* the tabs, because they are about the app rather than about either section, and hiding them behind a tab would mean a member who landed on the program on Sunday never saw the install prompt that iOS push depends on.

Which panel opens on a cold load is decided in `app.js` once, from the `/api/program` reply:

- an explicit `#program` / `#announcements` always wins — someone who followed a link asked for a section;
- otherwise the **Program** tab if the server said `open`, and the **Announcements** tab if not.

So the QR poster's plain `/` lands on the program during the meeting and on the announcements the rest of the week. The automatic choice is deliberately *not* written into the URL — stamping `#program` on a Sunday visit would strand that member on the closed message every day after. Only a tap the member made is remembered. The Program tab is always present; tapping it outside the window shows the closed message, short and centered.

**Notifications name their tab; the QR code does not.** Push payloads navigate to `/#announcements`, not to `/` (`weeklyMessage()` in `schedule-core.ts`, and the default link target of a manual send in `app.ts`). The two callers want opposite things from the same page: the weekly digest is *about* the announcements and fires at 08:00 Sunday, squarely inside the default 08:00–14:00 program window, so a bare `/` would hand the member the program under a body reading "tap to view the announcements" — while a scanned QR code has no subject of its own and wants exactly the entry rule. Naming the tab in the notification and leaving the poster's link bare gives each what it needs, and because the manifest's `start_url` stays `/`, a home-screen launch still gets the entry rule rather than inheriting the notification's hash. The admin's "a specific web link" option is untouched.

This makes the hash part of the *target* in the service worker's `notificationclick` handler: a window parked on `/#program` — or on a bare `/` the entry rule put on the program — is not "already there" and gets navigated. Admin tabs are still never reused.

A **cross-origin** target (the admin's "a specific web link") skips window reuse entirely and goes straight to `openWindow()`. Reusing one fails two ways: a match that ignores origin would count a link to another site's *root* as "already there" against any open window on `/`, so the tap would do nothing but focus the app; and `WindowClient.navigate()` rejects cross-origin in practice, so any other external link would fall through to the same bare focus. Opening a window is the one thing that reliably works from a notification, and it also stops a push yanking the member's app away to somewhere else.

### Dot-leader rows

Program lines read as two columns joined by dots, the way they do on a printed program:

```
Opening Hymn ... #19
... "We Thank Thee, O God, for a Prophet"
Presiding | Bishop Smith
```

A separator of **three or more dots, or a single bar, with a space either side** turns the line into `<p class="leader">` holding a left span, an empty `aria-hidden` span the CSS draws the leader on, and a right span. The spacing requirement is what keeps `Ratio 3|4` and a mid-sentence ellipsis out of it. The line directly under a row that opens with the dots and nothing to their left is the row's **note**, a fourth span inside the same `<p>` that the CSS sets on a line of its own, right-aligned under the value, regular weight and muted: a hymn's title under its number. It is explicit on purpose: a plain line under a row stays a paragraph, and a `... text` line anywhere else is ordinary text.

This is a **markdown-it block rule** (`src/markdown.ts`), not a pass over rendered HTML, and that is the security argument rather than a stylistic preference: a regex over `md.render()`'s output would be operating on a string in which the admin's text and our own markup are already indistinguishable, and a substitution there could reopen a tag markdown-it had escaped. Working on the *source* instead means both halves go back through markdown-it's own inline parser and out through its own escaping, so a name containing `<script>` is escaped by exactly the code that escapes it everywhere else. The rule emits its own tokens with their own renderer rules and never concatenates user text into markup.

It is registered `before('paragraph')` — which puts it after `table`, `code` and `fence`, so a real table and a code block still win the line — with an `alt` list that also makes it a paragraph terminator, so prose and rows can sit next to each other without a blank line between them. It is enabled on the **program** renderer only: `renderMarkdown()` (announcements) leaves a pipe in prose alone, which is why `markdown.ts` builds two instances rather than one.

Two CSS details in `styles.css` are load-bearing rather than cosmetic. The leader span is empty, so its baseline is its bottom margin edge and `align-items: baseline` drops the dotted border onto the text's baseline, where leader dots belong. And the row is a *wrapping* flex line on which neither side may shrink: when label and value don't both fit on a phone, the value drops to a line of its own under the dots, right-aligned, rather than the two squeezing each other ("Opening / Hymn" beside a title wrapping around a stub of dots, which is what shrinking produces). Each side is capped at the row's width once it has a line to itself, and the two `overflow-wrap` values decide how text past that cap breaks: the label at a space only (`break-word`), so "Organist" is never cut into "Organi / st"; the value between any two letters (`anywhere`), so a run-on name or a pasted URL can never widen the page. The note is a full-width item, which under `flex-wrap` is simply a line of its own.

### Hymn links

In a row whose label contains "hymn" (any case) and whose value is nothing but a hymn number — `#2`, `2`, `No. 2`, `#1001` — the number and the row's note link to that hymn on churchofjesuschrist.org, which opens in Gospel Library on a phone that has it (the `/study` pages are universal links). "Rest Hymn ... Ward Choir" or "Hymn ... 98–99" stays plain text, and the label is never a link. 1–999 is the 1985 *Hymns* (`/study/manual/hymns/<slug>`), 1000 and up *Hymns—For Home and Church* (`/study/music/hymns-for-home-and-church/<slug>`).

The address comes only from `src/hymns.ts`, a committed number → slug table that `scripts/hymn-index.mjs` (`npm run hymns`) generates from the two index pages, reading each hymn's number as the page prints it rather than from list order. It is never derived from the admin's text or guessed from a title. A number the table lacks — a hymn released since the table was generated — links to its book's index page instead. When the Church releases more hymns, run `npm run hymns` and commit the diff; the script fails without writing if either page parses to far fewer entries than expected.

It is a core rule run last (after linkify and smartquotes) on the members' renderer only. It reads the row's raw label and value and wraps the value's and note's already-parsed children in a link token pair, so the text keeps markdown-it's own escaping and the only new markup is the `<a class="hymn-link">`, whose attributes `renderAttrs` escapes. A note that already holds a link is left alone. The editor's instance (`editorMarkdownIt`) leaves the rule out, so a hymn link never becomes a link mark and is never saved into the Markdown. The links carry `target="_blank" rel="noopener noreferrer"` like every other link here: in an installed iPhone app an off-site page opens over the app (or Gospel Library opens) and the program is still there afterwards, and in a browser tab the program is not navigated away from mid-meeting. `styles.css` draws them in the row's own colour with a faint underline. `test/hymn-links.test.js` covers the table and the rule.

### Centered lines

A line written `-> Sacrament Meeting <-` renders as `<p class="centered">` — a heading-ish line in a program, an occasional flourish in an announcement. Same construction as the dot leaders above and for the same security argument: a **block rule** in `src/markdown.ts` whose content goes back through markdown-it's own inline parser, so `-> **bold** <-` is bold and `-> <img onerror=x> <-` stays escaped. Optional whitespace inside the arrows is tolerated; a line that merely contains `->`, or that lacks the closing `<-`, or that has nothing between the two, stays an ordinary paragraph.

Unlike dot leaders it is enabled on **both** renderers — `Presiding | Bishop Smith` is prose an announcement might legitimately write, `-> text <-` is not. Where both rules exist, **center wins** a line matching both shapes: the plugins are installed center-first, and since `before('paragraph')` inserts immediately ahead of `paragraph`, the ruler reads center_line, dot_leader, paragraph. So `-> Speaker ... Jane Doe <-` (pathological either way) centers the line and leaves the dots as literal text, the reading in which the outermost markers decide; `Speaker ... Jane Doe <-` is still a row, because there the arrows are not outermost.

### Headings and rules in a program

Plain Markdown headings are the program's section markers. Every heading level in a program body is bold at body size (`public/styles.css`, `.program .body`), so the levels differ only in the space they open above themselves. A heading is left-aligned like any Markdown heading; wrapping its text in the arrows centers it (`## -> Ward Business <-`), one syntax for both. That is a **core rule** in `src/markdown.ts` rather than a block rule, because the heading rule has already claimed the line: it runs between block and inline parsing, strips the markers from the heading's inline content and adds the `centered` class, and the stripped text still goes through markdown-it's inline parser, so the escaping argument above is unchanged. `##` opens a meeting section (a generous gap), `###` labels the smaller standing footer blocks (meeting times, classroom assignments), and `#` is a slightly larger title that the dated card heading mostly makes unnecessary. `####` and deeper are pinned to the `###` look so a stray extra `#` never falls to the browser's small left-aligned default. A `---` line is a light rule with more air than any heading, the break between the meeting and the footer. Centered paragraphs stay for the non-heading case, a special musical number announced mid-program.

For space anywhere else, **two or more blank lines** open a gap above the next block, where one blank line is ordinary Markdown and changes nothing. That is a second core rule: blank lines never become tokens, but every top-level block token carries `map`, the source lines it spanned, so the rule compares one block's end line with the next block's start and adds a `gap-N` class, one step per blank line beyond the first and capped at three so a stray run cannot push a section off a phone — CSS-only, top-level blocks only, both renderers. A line holding only `&nbsp;` still works as a spacer too.

### Retention

Programs name people, and nobody needs those names on a server for years. `program_retention_days` (default 90, measured from `program_date` rather than `created_at`, so a program written a week early doesn't outlive its own Sunday by a week) drives `purgeOldPrograms()`, which deletes each expired program's stored objects and attachment rows before the program row — the same ordering, and the same shared helper (`attachments.ts`), as the admin delete route.

Retention also decides how many programs the **dashboard** lists, via `dashboardProgramLimit()` — one per week over the retention window, plus eight of headroom for programs written ahead and for a week carrying a second row. That coupling is deliberate. The dashboard is the only place a program can be edited or deleted from, so one the list doesn't render is stranded until the purge happens to reach it — and against a *fixed* list length, retention decides how many are stranded and for how long. At the 90-day default a fixed 12 would hide about one row for about a week; at a year, forty rows for months. `MAX_DASHBOARD_PROGRAMS` is a ceiling on the arithmetic rather than on the policy: it is derived from `MAX_RETENTION_DAYS` (530 rows for the 522 Sundays a 3650-day window can hold), so against a validated setting it cannot bind, and tightening it below that range would strand rows at the far end, where nobody would notice for years. `test/programs-core.test.js` pins both halves of that.

Asking for a decade of Sundays is affordable because the query is a **projection**: `listRecentPrograms` selects `id, program_date` into a `ProgramListRow`, never `body_md`. A row costs tens of bytes instead of a whole program's text — which also means the busiest admin page does not pull every name the ward has published into memory to render a list of dates.

The card then shows what is actually in use — anything not yet past, plus the last six Sundays — and folds the rest into a collapsed `Earlier programs — N` archive carrying the same Edit and Delete controls, so the list stays short while nothing becomes unreachable.

A purge run is bounded by **two** caps, whichever binds first: `MAX_PROGRAMS_PER_PURGE` (4) programs, or `MAX_OBJECT_DELETES_PER_PURGE` (10) stored objects. Steady state is one program a week, so neither is reached in normal operation; they exist for a deployment that sat idle or a retention window an admin just shortened. Both are needed, because the cost has two shapes: a text-only program still costs three queries, while an image-heavy one costs a storage delete per image — and on Workers every one of those is a subrequest against a per-invocation budget of 50. Capping programs alone would leave three programs × ten images = thirty deletes in one invocation entirely legal. The object cap is checked at a program *boundary*, never mid-program, so nothing is ever left half-deleted — which is why the program cap is as low as it is: the last program of a run may still spend all ten object deletes on top of it. Worst case is 25 subrequests. The caps are a single-ward Worker's: when a sweep leaves expired programs behind, it clears the day's once-a-day marker so the next tick, a minute later, takes the next batch, and on Node and the many-ward host, which have no such budget, the sweep runs until nothing expired is left.

`maybePurgeOldPrograms()` is the periodic hook and runs **at most once per local day**, guarded by a `program_purge_last_run` setting holding that date. Node calls it at boot **and from a daily croner job** (`startProgramPurge`, 03:40 local) — boot alone would mean a process that stays up for months never purges at all; Workers calls it from the per-minute cron tick, where the common path is one settings read that finds today's date already recorded and returns. The marker is written *before* the sweep, so the next minute's tick can't start a second one — but it is **cleared again if the sweep throws**, so a transient database failure costs a retry rather than stalling retention for a whole day. (Storage failures never reach that path: `purgeAttachments` swallows them per object.)

## Resource pages

The **Resources** tab holds standing reference pages — the part of a ward website that is neither an announcement nor a program. Each is a row in `pages`: a title, a Markdown body, a publish flag and a manual order, and nothing else. No expiry, because a page is current until someone edits it; no place in the weekly digest, the "anything to send?" check or the email preview, because none of those iterate `pages`. That is the reason it is its own table rather than a `kind` column on `announcements`: nothing that walks announcements can pick a page up by accident.

The public tab renders each page as a `<details>` under its title, collapsed by default (a single page opens itself), so a page for one group does not push the rest down. The open/closed state a member set is carried onto the rebuilt nodes before `swapIfChanged()` compares them, so a resume refresh neither repaints nor folds the section they were reading. New pages are appended to the *bottom* (unlike announcements, which go to the top): the list reads as a table of contents.

Pages are behind the member gate like the announcements, rendered by the same `renderMarkdown()` (centered lines included, no dot leaders), and can carry images through the attachment machinery under `owner_type = 'page'`. Both roles may write them. The content policy on the dashboard applies to a page exactly as to an announcement — no personal contact details — and the page editor's image blurb adds the one thing pages make tempting: never a list inside an image, because `/images/:key` is ungated.

## Image attachments

An announcement, a page or a program can carry up to **10 images** — the flyer for an activity, a map, a photo, a printed insert. The rows live in `attachments`, keyed by `owner_type` ('announcement', 'page' or 'program') alongside the id; the bytes live behind `FileStore` (`src/filestore.ts`), the blob-storage counterpart to the SQL seam: a flat directory under Node (`uploadsPath`, by default `uploads/` beside the SQLite file, so one persistent volume still covers everything), an **R2 bucket** on Workers (`env.IMAGES`) when one is bound, and otherwise the **database** (`file_chunks`, base64 split into 1 MB rows under D1's 2 MB row cap, and left out of the JSON backup). The template config binds no bucket — enabling R2 asks for a payment card even on its free tier — so a ward deployed from the Deploy button stores images in D1. `app.ts` knows only the interface — `put`/`get`/`delete` by key — and the entry point picks the implementation, exactly as it does for the database.

- **Keys.** `[0-9a-f]{32}.<ext>` — 128 bits of randomness plus the extension, and the whole of the public URL (`/images/<key>`). The pattern is validated on the way in *and* the way out, which is what makes path traversal unspellable in the filesystem store rather than merely unlikely. On Node the extension is also how the content type is recovered, so a stored object is one file with no metadata sidecar to drift; R2 keeps the type as object metadata.
- **Ordering of writes.** Upload puts the object first and the row second (a row is what makes an image reachable); delete removes the object first and the row second (an orphaned object is invisible and billable, an orphaned row just 404s and is retried). That pairing lives in `attachments.ts` rather than in a route, because three callers need it: the two admin delete routes and the program retention purge.
- **Limits.** JPEG/PNG/WebP/GIF, 3 MB, 10 per owner, all enforced server-side. `owner_type` is validated against a whitelist rather than passed through, since an unrecognised value would create rows no delete path knows to clean up. The count cap is not aesthetic: deleting an owner deletes each object, and on Workers each of those is a subrequest against the free plan's budget of 50 per invocation.
- **In the browser.** The admin editor downscales before uploading — canvas to 1600px on the long side, JPEG q0.85 — so a modern phone photo (4000px, several MB) arrives small enough to matter on a phone's data plan. GIFs upload as-is, since re-encoding one to JPEG would silently drop the animation. The 3 MB limit is the backstop for whatever the browser didn't shrink.
- **Metadata.** The server strips what the browser's re-encode would have dropped and what it sends through untouched (a GIF, an image it could not decode, one its re-encode made no smaller): `stripImageMetadata()` in `image-meta.ts` walks the file's container — JPEG markers up to SOS, PNG and WebP chunks, GIF blocks — and never decodes pixels, because `app.ts` is runtime-neutral and a free-plan Worker has about 10 ms of CPU. What stays is the EXIF **Orientation** (rewritten into a 26-byte TIFF of its own — a sideways phone photo must still display upright) and the **colour profile** (JPEG APP2 ICC, PNG iCCP/sRGB/gAMA/cHRM, WebP ICCP); the rest of EXIF, its IFD1 thumbnail included, XMP, IPTC/Photoshop, PNG text and `tIME` chunks and GIF comments go. The same pass runs on the host's Import Backup and in `scripts/db-restore.mjs`, where a backup made before this existed may still carry it, and the row's `size` follows the stored bytes. A file the walk does not understand is stored unchanged: a corrupt file is the validator's problem, not the stripper's.
- **On the public page.** `/api/announcements` returns each announcement's image URLs alongside its HTML (as data, so the markup stays exactly the sanitized Markdown output); `app.js` renders a wrapping thumbnail row and a full-screen lightbox. The public payloads send an **empty `alt`**: the uploaded filename is kept on the row and shown in the admin editor, but what a clerk happens to name a file on their own machine ("bishop-storey-funeral-final2.jpg") is not published text.

**`/images/:key` is deliberately *not* behind the member access gate — for announcements and pages.** They are flyers for events the ward is advertising, the key is unguessable, and the list of keys is only ever handed to someone who already passed the gate — the announcements API is what produces them. Gating them would buy nothing and would cost the case that matters: an `<img>` rendering as a broken box because a cookie lapsed between the page load and the image fetch. The announcement *text* stays gated either way. The service worker treats these URLs as cache-first (the key never changes, so a cached copy can never be stale), unlike everything else, which is network-first.

**A program's images are as private as the program.** They are often a photo of the printed one, names and all, and a key alone used to be enough to load one for a year. So the route looks the key up (`attachmentByKey`) and serves an image that is not an announcement's or a page's only to a dashboard session (`sessionOf()`, any day) or to a member while that program's window is open on its own date (`mayViewPrivateImage()` in `app.ts`, the rule `/api/program` applies to the text), with `private, no-store` so neither the browser nor the service worker keeps it. Anyone else gets a 404, never a 403, so a key cannot be tested; an image no `attachments` row names is not served at all. Images on a New form nobody has saved (`pending`) fall under the same rule, which leaves them to the dashboard.

**Inline images in Markdown** draw only from the ward's own uploads (`/images/<key>`). Anything else in `![…](…)` is rendered as a link to it (or, for a non-web address, its words), so a body cannot make every member's phone fetch another site on each load — a tracking pixel. Members' renderers only: the editor parses with the same rules, and rewriting there would save the link back into the source. The visual editor cannot insert an inline image; images are attachments.

## The meeting time

A clerk is asked for one timing: when sacrament meeting starts — a day of the week (Sunday preselected) and a local time — in **Ward Settings → Sacrament Meeting**. `meeting.ts` derives the rest: the **program window** runs that day from an hour before the start to two hours after (10:30 → 9:30 AM–12:30 PM), and the **weekly notification** goes out an hour before the start, as the program becomes visible — before church rather than in the middle of a meeting. Both are clamped to the meeting's own local day, never wrapping past midnight: an opening that would fall before 00:00 is 00:00 (window and notification alike), and a close past the day's end is 23:59. The form accepts 6:00 AM to 10:00 PM (`EARLIEST_MEETING`/`LATEST_MEETING`), wide enough for any real meeting and narrow enough that an AM/PM slip is refused rather than hiding the program all day; `deriveTiming()` clamps anyway, for any time.

The meeting time is stored on its own (`meeting_time`, `{dow, time}` JSON in `settings`, no schema change), but **nothing reads it to decide anything**. `saveMeetingTime()` writes the derived window through `setProgramSettings()` (keeping the closed-page wording and retention) and the schedule through `setScheduleSettings()` — the call the old Day and Time form made — so `/api/program`, the cron tick, a hosted ward's alarm, the closed-program message and the summary strip read exactly the settings they always did. The schedule is only written when its day or time actually changes: a move is stamped (`schedule_set_at`) and the runtime hook fires exactly as from the form, while re-saving the slot already in force is not a move and so cannot veto a catch-up for a send that is still owed. A hosted ward needs nothing extra — its Durable Object re-derives the alarm after every write request. The stored value is for the dashboard: to show it, and to tell (`timingStatus()`) whether the window or schedule has since been changed by hand.

**Advanced Timing**, the row beside it, holds the detailed forms — the program hours, closed message and retention (`/admin/programs/settings`), and the weekly day and time (`/admin/schedule`) — for a ward whose hours are not simply "around the meeting". Its value reads *From meeting time*, *Custom* when either differs from what the stored meeting time derives (or, before one is saved, from the shipped defaults), or *Default*. Saving the meeting time resets both, and its form says so ("This replaces your custom times.") when they are custom. The form's preview line ("Saving sets the program hours to 9:30 AM–12:30 PM and the weekly notification to Sundays at 9:30 AM.") is recomputed by a few lines of inline script mirroring `deriveTiming()`, rendered by the server for the stored time, and repeated by the save's flash, so the page says the same with script off. The Programs card's "Change the Hours" and the Notifications Day and Time row jump to this row with the dashboard's section links (`data-section`; `reveal()` opens a settings row it lands on).

Like the window and the schedule, the meeting time is local wall-clock time, so a timezone change keeps all three at the same local time (`scheduleRezoned`, not a move) and the timing stays *From meeting time*. Get Started's second step is "Set your meeting time", ticked once one is stored; a ward that existed before keeps its timing untouched until someone saves one.

## Scheduling

The send **day-of-week and time** live in the `settings` table (`schedule_dow`, `schedule_time`) and are set from the meeting time (above) or directly under Advanced Timing; they're seeded once to a hardcoded default (`DEFAULT_SCHEDULE` = Sundays 08:00) on first run. Everything runtime-free about the weekly send — the settings, the message, and the timezone arithmetic for the next/previous/due occurrence — is in `schedule-core.ts`, which imports no Node built-in and no croner. Both runtimes call `queueWeeklySend()`, which no-ops when `auto_send_enabled` is off.

A local time on a daylight-saving Sunday is resolved the way croner resolves it (`instantAt`), so Node and Workers agree on the instant: a time the clocks skip (02:30 in Denver in March, 00:30 in Santiago in September) is read with the offset from before the jump and so lands an hour later, on the same date; a time the clocks pass twice is the first pass. Only a hand-set Advanced Timing time can fall in those hours — a derived one is 05:00 or later. The program window's closing instant (`programWindowClosesAt`) goes through the same function.

### Sundays that don't send

Two of them, for different reasons, and both land in the same place.

**Nothing posted.** `queueWeeklySend()` skips when `countPublicAnnouncements()` is 0. A digest reading "Tap to view the announcements" that opens an empty list is worse than silence, and on an app whose whole pitch is roughly one notification a week it is the one push a member could fairly call spam.

**A Sunday the ward chose.** General Conference, a stake conference. Rows in `send_skips`, keyed by the **local date** rather than by a slot key — an admin who later moves the send from 08:00 to 07:30 has not changed their mind about Conference, and a slot-keyed row would silently stop matching. Checked *ahead* of the emptiness test, because it outranks it: the history should read as the reason somebody gave, not as "no current announcements". Editable by **both roles** — an editor can already cause a week to be skipped by publishing nothing, so gating the explicit control would protect nothing and only oblige the person most likely to know Conference is coming to go and ask.

Either way the skip is recorded by `recordSkippedSend()` as a **real send**: a `send_log` row typed `skipped` carrying the reason, plus a `send_batches` row against the slot, born `done` with no queue rows so no drain or sweep adopts it. That one decision does three jobs. The dashboard's Recent Sends card renders it with no extra fetch, answering "why did nothing go out?" in the place the question is asked. The slot becomes covered by the same `UNIQUE` index that stops a double-fired cron from sending twice, so `uncoveredSlot()` and `enqueueSend()` — every "has this occurrence been dealt with?" check already in the codebase — answer correctly with nothing new to ask. And because the record is separate from the *intent*, deleting a `send_skips` row afterwards cannot resurrect a send that was already decided against: tidying the list on Sunday afternoon is safe, which is the whole reason a spent skip never needs tidying by hand.

That last part is deliberate, because the alternative is a real hazard. Both runtimes will still pick up a missed occurrence for `CATCHUP_GRACE_MS` — twelve hours — so a skip deleted the same morning could let a restart that afternoon deliver exactly the digest it existed to suppress. Spent skips are therefore removed by `pruneSpentSkips()` on the same once-a-local-day clock as the program retention sweep, two days back, and the dashboard lists only dates from today onward. An admin never learns any of this: a date that has passed leaves the list at once and its row goes on its own. A skip dated on a weekday the send never fires on is kept but flagged on its row, since silently accepting one would mean someone "skips" Conference and gets the notification anyway.

A **manual** send is never skipped — an admin who typed a message and pressed the button meant it.

Both runtimes key a send to the **occurrence** it covers, not to the moment the code happened to run: `slotKey()` (`YYYY-MM-DDTHH:MM` local) names the occurrence, it is stored on the send, and a `UNIQUE` index on `send_batches.slot` makes enqueueing it idempotent. That is the guard against a cron trigger firing the same minute twice, which Cloudflare has been observed to do — and it only works if both runtimes agree on the name, which is why the croner callback derives the key from `previousSlotAtOrBefore()` rather than from `new Date()`. A key taken from the clock would let a callback that fires thirty seconds late mint a second key for the same Sunday, and two keys means the index guards nothing.

The slot key includes the time, so a schedule moved later on the same day — the 08:00 digest goes out, and at 08:30 a clerk corrects the meeting time, which moves the slot to 10:00 — would name a slot nothing covers. So there is also **one scheduled digest per local date**: `queueWeeklySend()` and `uncoveredSlot()` both treat a slot as covered when a `scheduled` send already went out that day (`scheduledSendOnDate()`); a *skip* earlier that day does not count, so a later slot that finds something to say still says it. And switching auto-send back **on** moves the catch-up floor (`schedule_set_at`) to now, as a schedule change does (`setAutoSendEnabled()`): while it was off a passing slot was simply not sent, and without the move a ward that turned notifications off for Conference weekend and on again at 15:00 would get the 08:00 digest at 15:00.

**On Node**, `schedule.ts` holds a live **croner** job in the process. Saving in the admin calls `setScheduleSettings()` → `applySchedule()`, which stops and rebuilds it — no restart needed. A startup catch-up (`catchUpMissedSend`) covers an occurrence missed while the process was down, and the per-minute job (`startRetryDrain`, at :30 so it never races the croner job's on-time send) asks the Workers tick's own `uncoveredSlot()`, so an occurrence whose enqueue failed — a locked database, a full disk — is retried within the same 12-hour grace rather than lost for the week.

**On Workers** there is no job to rebuild: the cron trigger is `* * * * *` (every minute, UTC) and each tick decides for itself, in this order:

1. **Is the last scheduled occurrence covered?** `uncoveredSlot()` answers it, and the tick asks *first* — whatever the queue is doing. It is a question about whether a `send_batches` row exists for that slot, not about what minute it is now, and it holds for the same 12-hour `CATCHUP_GRACE_MS` Node's boot catch-up uses, with the same two vetoes (auto-send off, or a schedule changed *after* the occurrence). It goes first because draining first and then checking a 10-minute window would silently skip the whole Sunday whenever the window ran out while the queue was busy: a ward large enough to still be draining at 08:10, a manual send at 08:05, or a few ticks Cloudflare delayed or dropped.
2. **Drain one chunk**, if anything is queued (including whatever step 1 just enqueued).
3. Otherwise **settle a stale send**: a `send_batches` row still `pending` with no queue rows is what a kill between the last commit and `settle()` leaves, and it would otherwise sit in the history forever claiming zero recipients. One per tick.
4. Otherwise **housekeep**: the program retention sweep, at most once a local day.

Steps 2–4 are exclusive so one tick never spends two budgets' worth of subrequests. The tick itself is `runTick()` in `tick.ts`, shared with the many-ward host. `scheduled()` awaits only the *core* half of boot (config, driver, schema) — never the app shell, whose seven `ASSETS.fetch` reads would otherwise be spent every cold-started tick on a page nobody is looking at.

**On the many-ward host** each ward runs the same `runTick()` from its Durable Object's **alarm**, with `drain: 'all'` (the queue drained to empty, the steps not exclusive), and sets the next alarm to `nextWake()` — see [The many-ward host](#the-many-ward-host). An hourly cron only pokes every ward, as a safety net for a lost alarm.

## Member access gate

The first middleware in the chain ([src/access.ts](../src/access.ts) + `app.ts`) gates the page and the announcements API. Static/PWA assets (`manifest`, `sw.js`, `app.js`, `install.js`, `styles.css`, icons), `/healthz`, `robots.txt`, `/api/access`, `/images/*` (see [Image attachments](#image-attachments)), and `/admin` + `/admin/*` (own auth) stay open. The admin exemption is those two forms exactly, not the prefix `/admin`, which would also have exempted `/administrivia` and anything else beginning with those six characters. The exemption is checked **before** any credential lookup, so a static asset costs no round trip to D1.

The gate is **always on**: the first code is minted at boot (`ensureAccessCode`), so a fresh install is gated from its first request, and admins rotate codes from the dashboard. Codes never live in config, so a redeploy can't resurrect one an admin retired.

### Four kinds of credential

| Kind | Where it lives | Lifetime | Purpose |
|---|---|---|---|
| **Shared code** (`access_codes`) | Printed QR posters, the admin share link | Until rotated, then a grace window | The credential an admin hands out in bulk |
| **Invite** (`access_tokens`, `kind='invite'`) | A member's share sheet (`#i=…`) | Set in the dashboard, 1–365 days (default 30), unlimited uses, **max 5 live per device** | Lets a member pass the app to a friend without copying the shared code onto their phone |
| **Email link** (`access_tokens`, `kind='email'`) | The "get the app" line in the weekly email and its PDF (`#i=…`) | 14 days, fixed, unlimited uses; **one new one at most every 3 days** | Lets the email the ward already sends carry a way in, without putting the shared code in every archived copy |
| **Device** (`access_tokens`, `kind='device'`) | One installed app's manifest `start_url` | 5 years, fixed | Cold-launch unlock for an installed PWA, decoupled from rotation |

The device lifetime is a constant rather than a setting on purpose: it exists to outlive code rotation, so shortening it re-introduces the stranding it prevents and lengthening it changes nothing observable.

**The email link** is minted by `mintEmailLink()` when a clerk ticks *Include a link to the app* in the dashboard's Preview (`POST /admin/announcements/preview/link`, both roles). It is its own kind rather than a member invite because an email is archived and forwarded: it wants a fixed short life, not the dashboard's invite setting, and it belongs to no device, so the per-device cap has nothing to count. What bounds it instead is reuse — a live link minted in the last three days is handed back rather than joined by another, so a week's exports share one credential and the next week's email gets a full fortnight of its own. The line names the last whole day the link works (the day before its expiry, in the ward's timezone) so an old email explains itself. Like an invite it survives a code rotation and a sign-everyone-out; its short life is the only containment.

**Expired tokens are deleted** a month after they lapse, whatever their kind (`purgeExpiredAccessTokens()`): on boot, and once a day on the program purge's clock, because a Node process that stays up never boots. The month is tidiness, not enforcement — every lookup already filters on the expiry.

**Invites are capped at five live per device** (`MAX_LIVE_INVITES_PER_DEVICE`, recorded on the token's `device_id`). An invite is a real credential — unlimited uses, thirty days, and it survives a code rotation and a sign-out of browsers, since neither touches `access_tokens` (only *Everyone, including installed apps* does) — and a per-IP rate limit alone would not bound it, since that is per-isolate on Workers and trivially waited out. Past the cap `mintInvite()` hands back the newest live invite instead of minting a sixth, so the share sheet still shows a working link and nothing in the member flow changes; only the number of live credentials one cookie can put into the world is bounded. `/api/invite` therefore reads the member cookie and nothing else: a request whose only credential is in `?code=` has no device to count against, and is a 401. That path was once uncapped — one leaked invite, presented in `?code=` without a cookie, could mint invites without end — and the share sheet only ever runs in a page that already holds the cookie, so it loses nothing.

`redeemCredential()` compares a candidate against every *usable* shared code (the active one plus any retired code still inside its grace window) in constant time and without short-circuiting, then falls back to an indexed token lookup — safe there, since tokens are 256-bit random values.

### Flow

A request with a valid `pushannounce_access` cookie passes, and the cookie is re-issued on every request for a sliding 5-year expiry — an idle timeout, not a cap, since any visit slides it forward. (Chromium and Firefox clamp any cookie to 400 days per RFC 6265bis, so only Safari honours the full length; installed apps are covered regardless by their `start_url` device token, which carries the same 5-year life.) Otherwise a `?code=` matching any usable credential sets the cookie and — for a page visit — redirects to the clean URL. With neither, page navigations get the **soft gate page** (no content) and `/api/*` gets a 401.

That clean-URL redirect runs the requested path through `http.ts#samePathOnly`, which collapses leading slashes and backslashes so the target can only ever be a path on this origin. Echoing `c.req.path` back verbatim would make `//evil.example.com/x?code=<valid>` a 302 to another origin — an open redirect wearing the ward's own domain.

**Credentials ride in the URL fragment.** The links the app hands out (`PUBLIC_ORIGIN/#code=…` for the admin share link and QR, `#i=…` for member invites) put the credential after the `#`, which browsers never transmit. That keeps it out of server and proxy access logs and out of the fetch a chat app makes to unfurl a pasted link. Since the server can't see a fragment, the gate page carries a small inline script that reads it, `POST`s it to `/api/access` (rate-limited, gate-exempt), and then `location.replace`s to the clean URL, with leading slashes and backslashes collapsed to one as `samePathOnly` does, since the gate is served at any path and `//evil.example/x` would otherwise be another site. `?code=` is still accepted for the one context that needs it: installed apps' `start_url`.

Notification `navigate` URLs carry **no** credential — every push recipient subscribed from an already-unlocked page, so they hold a cookie by definition. `Referrer-Policy` + `noindex` (meta, header, robots.txt) keep the page out of referers and search engines.

### Cookie signing

The member access cookie is `v1.<deviceId>.<issuedAt>.<HMAC-SHA256>`, signed with a key that is generated once and stored in `settings.access_cookie_secret`. This is deliberately **separate from `config.sessionSecret`**, which is derived from `ADMIN_PASSWORD` and signs the admin session: changing the admin password ends admin sessions without logging out the entire ward. The `deviceId` is what ties an installed app to its device token — and redeeming a device token *adopts* the id already stored on it rather than minting a new one, so a cold launch keeps the credential it presented. Minting afresh there would quietly orphan a live five-year token on every re-unlock.

There is no env override for this key. The one thing an override would buy — forcing every member to re-unlock — is the dashboard's sign-out option on **Issue a New Code**, which rolls the stored key (`resetAccessSecret()`). Keeping it out of the environment means there's no value to lose or mistype into a ward-wide lockout, and no way for it to drift from what the database holds.

Two details of *how the key is read* matter on Workers, where many isolates run at once:

- **Minting is insert-if-absent, then re-read.** `loadOrCreateSecret()` mints a candidate, writes it with `setSettingIfAbsent()` (`ON CONFLICT(key) DO NOTHING`), and then reads the row back, so the loser of a race adopts the winner's secret. Writing unconditionally would let the loser sign cookies with a key it had just overwritten — they would verify for as long as that isolate lived and then stop, at random.
- **The per-isolate cache has a 60-second TTL.** The TTL is what makes a sign-out reach every isolate: a cache that lived forever would make it a *local* event, where the isolate that handled the button press forgets every cookie and every other isolate goes on honouring them until Cloudflare happens to recycle it. Within the TTL the in-flight promise is shared, so concurrent requests make one read. This is a read discipline only: a member's cookie stays valid across the re-read.

`hasAccess()` also **checks the signed `issuedAt`** against the same 5-year `MAX_AGE` the cookie claims. Without that check a cookie lifted off a device would outlive its `Max-Age` indefinitely, since `Max-Age` is only a request to the browser.

### Rotation

The dashboard's **Issue a New Code** control mints a fresh code (16 chars from an unambiguous alphabet, ~79 bits) and puts the outgoing one on a grace clock — a week by default, long enough to reprint the QR posters on a bulletin board but short enough that a leaked code actually stops (it was a year, which left two live codes for a year); the form also offers 30 days, 6 months, a year, immediately and indefinitely. Members who have already unlocked are unaffected in every case: their cookie is not derived from the code. The grace chosen when issuing a new code is also the ceiling for every older retired code still in its grace — "Stop it immediately" ends them all, and a later "Indefinitely" never extends an older code. Rotation history, including whether each old code still works, is listed on the dashboard.

Only one thing must be re-issued after a rotation: **printed QR codes** (and printed flyers).

Evicting members is a separate, deliberately louder choice on the same form, **Who is signed out**: *Everyone who used a browser* rolls the cookie signing key, which invalidates every access cookie at once, and *Everyone, including installed apps* also deletes every saved credential (below). Either forces the grace to zero, since a retired code still working would let the evicted party straight back in. Installed apps re-unlock silently on next launch via their `start_url` device token, so the first lands on browser-only visitors.

**iOS installed-PWA unlock.** An installed iOS PWA has its own cookie store, separate from Safari, so a freshly installed app would otherwise launch `start_url` with no cookie and hit the gate. To fix this, `manifest.webmanifest` is served dynamically and embeds a credential in `start_url` (`/?code=…`) **only for already-authenticated requests** — the `<link rel="manifest">` uses `crossorigin="use-credentials"` so the manifest fetch carries the cookie. At install time the user is authenticated in Safari, so the captured `start_url` includes it and every cold launch re-grants access; an anonymous request still receives a credential-less `start_url`.

That credential is a **per-device token**, not the shared code, and the reason is rotation: iOS freezes `start_url` at install time and re-fetches the manifest unpredictably, so a shared code baked in here would have to stay valid forever or installed devices would lose their cold-launch unlock whenever an admin rotated — which would defeat rotating at all. The token is keyed to the cookie's `deviceId`, so repeat manifest fetches reuse one row. This path depends on iOS fetching the manifest with the member cookie (`crossorigin="use-credentials"` on the link) and launching at `start_url`; **verified on a real iPhone** (iOS 18): a fresh Safari install minted a `device` row in `access_tokens`, and after a sign-out of *Everyone who used a browser* the installed app still opened straight to the announcements while a Safari tab on the same ward showed the gate. An app that got back in by *pasting* a code holds no token and does not get this (see below).

**After *Everyone, including installed apps*** the device token is gone, and the frozen `start_url` opens the gate on every launch. An installed app has no address bar, and a link tapped in Messages or Mail opens Safari, whose cookies are not the app's — so the gate shows a **Paste your ward link** field when it runs standalone (`display-mode: standalone` or `navigator.standalone`). It takes a whole link (`#code=`, `#i=`, `?code=`) or a bare code and posts it through the same `/api/access` exchange as a fragment, so it is rate-limited the same way and needs no endpoint of its own. The app then holds a cookie and its dead `?code=` is ignored beside it — but that cookie is all it has, so a later browser sign-out locks it out again until the member pastes once more or reinstalls from Safari (which captures a fresh device token). **Verified on a real iPhone** (iOS 18, installed app, when these were separate buttons): the field is absent in a Safari tab and present after the revoke; a whole link and a bare code each unlock; the app stays unlocked across force-quits; a sign-out locks it again and a second paste reopens it.

## Declarative Web Push

`buildPushMessage()` emits the Declarative Web Push shape (`{ web_push: 8030, notification: { title, body, navigate, lang } }`). On Safari/iOS 18.4+ the browser renders it natively without waking the service worker; on every other browser the service worker's `push` handler reads the same `notification` fields and calls `showNotification()`. `navigate` is made absolute via `PUBLIC_ORIGIN` when set.

## Data persistence

Cloudflare **D1** on Workers; a SQLite file at `DATABASE_PATH` (default `./data/app.db`) on Node; each ward's Durable Object on the many-ward host. The tables are the `CREATE TABLE` statements in `SCHEMA` in `db.ts`, the one list everything else (the backup, the reset and restore scripts) reads. Uploaded image *bytes* live wherever the [image store](#image-attachments) puts them: in the database's `file_chunks` on a Worker with no R2 bucket (the template's default), otherwise in R2 or in `uploadsPath` (Node) — so a Node deployment has **two** things on its volume to back up, and in no case does the JSON dump carry the images. The entry point installs a driver and calls `initDb()`. There is no separate migration step on Workers — an isolate brings the database up to date before its first query — so `initDb()` is **version-gated**: it reads a `schema_version` settings row (one query) and, when that is current, does nothing else. Only when it isn't does it run the `CREATE … IF NOT EXISTS` list (one statement at a time, because D1 cannot reliably execute a multi-statement script) plus the guarded `MIGRATIONS` — columns an existing table needs, which `CREATE IF NOT EXISTS` cannot express. Each migration probes for its column with a `SELECT` before altering (a probe that works identically on D1 and better-sqlite3, unlike `PRAGMA`) and swallows a duplicate-column error on top of that, so a half-migrated database heals and two isolates racing are harmless: the DDL is idempotent and the version write lands last with the same value from both. Running the twenty-odd DDL statements on every cold start would spend nearly half of the fifty subrequests an invocation is allowed. `seedIfEmpty()` is gated by a `seeded` marker for the same reason — and so two cold isolates cannot both insert the sample announcements. On the Node deployment **the directory holding the file must be a persistent volume** or subscriptions are lost on redeploy.

`GET /admin/backup.json` dumps every row of every table as JSON — a portable logical dump rather than a SQLite file image, so it works the same on either driver — less three settings-table things. Two would make it a way into the dashboard: the `admin_people_secret` setting (which signs people's sessions) and the `admin_invites` rows (live sign-in links); after a restore a new secret is minted, so everyone signs in to the dashboard again, and members are unaffected. The third, `vapid_keys` (the VAPID pair the app generated), would make it a way to every member's phone: beside the `subscriptions` rows — each endpoint with its `p256dh` and `auth` — the private key is all that a push needs, and a push service ties a subscription to the key it was made with, so a leaked pair has no rotation short of every member re-subscribing. Any admin can take the download and it is meant to sit in a folder for years, so the pair never goes out in the clear: with a `BACKUP_SEAL_KEY` set it travels **sealed** (`seal.ts`: AES-256-GCM through WebCrypto, a random IV per call, the setting's name as additional data so a blob cannot be replayed into another setting; the row is `vapid_keys_sealed`, a versioned JSON blob `{v, alg, iv, ct}`), and with none it is left out. The restore side opens the blob first (`unsealBackupTables`, in `seal.ts` so the restore script can import it without a build) and only then plans: a pair that opened is restored like any setting, one that did not (another deployment's key, or none) is dropped — `planRestore` drops a stray `vapid_keys_sealed` row too, so a blob nobody can read is never written as a setting — and `KEPT_UNLESS_IN_BACKUP` keeps the target's pair when the plan has none. So a ward restored over itself sends as before, a restore onto a fresh database with the same seal key sends as before, and a restore anywhere else sends with the pair that database minted, which the installed apps re-subscribe against (the service worker compares the key it subscribed with to the server's) while the rest turn notifications on again. The many-ward host's operator export seals the pair the same way under the host's key (plaintext only on a host with none) and keeps the other two, so moving a ward on its host signs nobody out and re-keys nothing. The table list is derived from the schema, so a new table is included automatically. It is the data half of the full backup; see [Backups and restores](#backups-and-restores).

The database is also the credential store — it holds the access codes, the invite/device tokens, and the member cookie signing secret. That makes every backup a sensitive download; treat a backup file the way you'd treat the codes themselves.

## Backups and restores

**The full backup is a ZIP built in the admin's browser.** Settings → Backup → *Download Backup (ZIP)* runs `public/backup-zip.js`: it fetches `/admin/backup.json`, then each image the `attachments` rows name from `/images/<key>`, one at a time with a progress line, and writes `backup.json` (the download byte for byte), `images/<key>` and a `manifest.json` (format version, schema version, time, hostname, image count and bytes, and the images that could not be fetched, with why) with `public/zip.js`. The server does nothing new: CRC-32 over tens of megabytes of images would blow far past a free-plan Worker's ~10 ms of CPU, while the browser already has the images one ungated URL away — from R2, the disk or D1's `file_chunks`, since `/images/:key` serves whichever store the deployment uses. The writer stores rather than deflates (JPEG/PNG/WebP/GIF do not compress, and were downscaled on upload) and refuses zip64 sizes rather than writing them wrong; the reader also inflates deflated entries where `DecompressionStream('deflate-raw')` exists, so a backup re-zipped by an operating system still loads. The same `zip.js` runs in the operator's page and, through `vm`, in `scripts/db-restore.mjs`; `test/zip.test.js` checks its output with an independent reader and `node:zlib`'s CRC, and `unzip -t`.

**What a restore means is one module, `src/restore.ts`, used by both restorers** — `scripts/db-restore.mjs` (which imports the TypeScript directly; Node strips the types, so a restore needs no build) and the host's Import Backup. A restore is a replace: every table is emptied and refilled with ids kept, and a table the backup predates is left empty, so the result is the backup's ward rather than a blend of two. The sending tables are the exception to "as it was": `send_queue` is emptied, a `pending` send is closed, and `schedule_set_at` (the catch-up floor) is set to the restore, so neither a backup taken mid-send nor one older than this morning's digest sends anything a second time. A table this version lacks is refused, a backup from a newer schema is refused, and a column this version lacks is dropped and reported (`subscriptions.label`, from an early version). Table and column names come from the schema — `restoreTarget()` in `db.ts` parses its own `CREATE TABLE` statements, and the script parses the same statements out of the source — never from the file. **`file_chunks` is never touched**: the JSON never carries image bytes, so emptying it would delete every image of a D1-only Worker restored over itself. The script writes a ZIP's images to a folder and prints the command for each store (an R2 loop, a copy into `UPLOADS_PATH`, or `--d1-images`, which puts them into the SQL as `file_chunks` rows of 90,000 base64 characters, under D1's statement-size limit). `db-restore.mjs` skips a backup image whose extension does not match an allowed image type, and `/images/:key` always serves the type its extension implies. It takes the deployment's `BACKUP_SEAL_KEY` (the environment variable, or `--seal-key`) to open the sealed push keys, and says on the terminal whether they opened, stayed locked, or were never there.

### Import Backup on the many-ward host

The operator page's dialog unpacks the ZIP in the browser, posts the backup's JSON to `/wards/:id/import`, then posts the images in batches of about 2 MB (base64, in JSON) to `/wards/:id/images`; the API has the same two routes under `/__operator/`. Both are behind the operator's session and Origin check (or the bearer password), the import needs the ward's address typed out, and `bodyLimit` caps them at 12 MB and 8 MB. The operator app only forwards; the work happens in the ward's Durable Object (`WardDO.importBackup`):

- **Planned outside, written inside one transaction.** `prepareImport()` (`ward-import.ts`) validates the file and the push keys and builds the plan with nothing written. The rows are then written by the ward's own boot, **inside the boot's `storage.transaction()` and ahead of its `initDb()`**, so a backup from an older schema is migrated in the same all-or-nothing step, and a failure anywhere — a duplicate id, a migration — rolls back to the ward as it was, in storage and in memory.
- **A fresh tenant, not patched caches.** The ward reboots into a new `Tenant` on the restored database, so every `tenantLocal()` slot — the config with its push keys and address, the ward settings, the member-cookie and people secrets' caches, the drain lock — starts empty; a slot added later cannot be forgotten. The old tenant and app are kept until the commit and put back if it fails. `blockConcurrencyWhile` keeps every other request and the alarm out meanwhile. The alarm is then re-derived (`reschedule()`), as after any write.
- **What the ward keeps of its own.** Its `host_ward_*` settings (its id, address, suspension), whatever the backup says — a backup from another hosted ward carries that ward's. A learned `public_origin` from another address is dropped, since it would outrank the ward's own. Its `ward_settings` (name, timezone) and its stored VAPID pair when the backup has none: the original code read both from the environment. `seeded` is set, so the sample announcement is never added to a restored ward.
- **Subscriptions** must be at a real push service, by the rule `/api/subscribe` applies (`isPushEndpoint` in `push.ts`; outside production any https hostname): every one is a URL the host POSTs to each week, and a backup is a file. The rest are left out and counted in the warnings. The production flag is handed in by the ward (`ImportTarget.production`) because the plan is built outside the ward's tenant, where `config` has nothing to answer with.
- **Push keys.** The backup's sealed pair is opened first with the host's `BACKUP_SEAL_KEY` (`ImportTarget.sealKey`, handed in like `production`), and a blob that does not open is dropped before the planner sees it. Supplied keys are checked by signing with the private key and verifying with the public one, then stored as the generated pair is (`vapid_keys` in `settings`, read by `loadStoredIdentity()`), with an optional subject that, like the pair, yields to the environment. Otherwise the backup's own pair (opened, or in the clear from a host with no seal key), else the ward's, else a new one — and the summary says which, and whether a sealed pair opened (`push.sealed`: `opened`, `locked` or `none`), and warns when the pair stayed locked or subscribers came without their keys.
- **Images.** A key is accepted only if a restored `attachments` row names it, has the upload path's shape and limits (type by the row's content type matching the key's extension, 3 MB), and its bytes really are that type (magic numbers). An image already present is skipped, so a retry or a second import is idempotent. They go to the ward's own store: on R2, under the ward's prefix (`<Durable Object id>/<key>`, `withPrefix` in `filestore.ts`), so `/images/<key>` on another ward can never serve them; without R2, the ward's own SQLite `file_chunks`. The previous ward's images that the restored rows no longer name are deleted after the commit.

### Export on the many-ward host

The operator page's **Export** makes the same ZIP as a ward's own Backup button, with the same code: `public/backup-zip.js`'s `download()` takes the URLs to fetch (`buildBackup()`'s `dataUrl`, `imageUrl(key)` and `name`, defaulting to the dashboard's), and the page, which loads it from its own `/backup-zip.js` (served only to a signed-in operator, like `/zip.js`), points it at `/wards/:id/export` for the data and `/wards/:id/images/:key` for each image. The page cannot fetch the ward's own `/images/<key>` instead: that is another origin, and an image carries no CORS headers to read it by. The image route forwards to the ward's private channel (`image` in `WardDO.internal`), which checks the key's shape (`isValidKey`) and reads it through the ward's own `files` store — its R2 prefix or its `file_chunks`, exactly as `/images/:key` and Import's writes do — so one ward's route can never reach another's images; an unknown or ill-formed key is a 404. It is behind the operator's session (a lapsed one is a 401 in JSON, not the sign-in redirect a fetch would follow and call a success; `buildBackup()` also refuses a redirected data response for the same reason) and answers `private, no-store`, as every operator response now does. The API has the same image route under `/__operator/`; its `/wards/:id/export` stays the JSON, data only, with the ward's push keys sealed under the host's `BACKUP_SEAL_KEY` exactly as `/admin/backup.json` seals them (`sealBackupSettings`), so Import Backup takes either file alike. `test/host/export.test.js` covers the route (operator only, the right bytes, no other ward's, 404s) and a round trip — ward A's ZIP built by `backup-zip.js` in a `vm` against the page's routes, imported into ward B through the page's Import, identical rows and images — and `test/host/operator.test.js` reads an image from `file_chunks`, without R2.

`test/host/import.test.js` covers an export of one ward imported into another (identical content and ids, the member cookie working, people and passkeys present, images byte for byte, the alarm re-derived), a dropped column, refusals that leave the ward unchanged, a failure part-way through, the confirmation, operator-only access, the push keys (a sealed pair opened by the host, one sealed elsewhere staying locked, and supplied keys replacing either), and image validation; `test/restore.test.js` covers the planner, the import rules, signing with an imported pair, `db-restore.mjs` on a JSON and a ZIP (and with a sealed pair, under the right key and a wrong one), and the backup download with and without a seal key; `test/seal.test.js` covers `seal.ts` itself.

## Configuration (environment)

See [.env.node.example](../.env.node.example) (Node) and [.dev.vars.example](../.dev.vars.example) + `wrangler.jsonc` (Workers). Key vars: `APP_NAME`, `APP_SHORT_NAME`, `APP_DESCRIPTION` (all required — the app's displayed identity and PWA manifest), the optional `APP_FOOTER` and `LINK_TEXT` / `LINK_URL` (these and `TZ` are starting values the dashboard's Ward Settings overrides), `ADMIN_PASSWORD` (the only secret a Workers deployment must supply), `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` and `PUBLIC_ORIGIN` (each optional — see below), `BACKUP_SEAL_KEY` (optional; seals the push keys inside backups, see [Data persistence](#data-persistence)), `TZ`, `NODE_ENV` (`production` marks cookies `Secure`, accepts subscriptions only to the known push services, and on Node makes `PUBLIC_ORIGIN` required), plus `PUSH_CHUNK_SIZE` (subscribers per drain, default 12), `IMAGE_QUOTA_MB` (image storage per ward, default unlimited) and the Node-only `PORT`, `TRUST_PROXY`, `DATABASE_PATH` and `UPLOADS_PATH` (images; defaults to `uploads/` beside the database file). The many-ward host adds `OPERATOR_HOST`, `WARD_DOMAIN` and `WARD_OWNER_SIGNIN` ([above](#the-many-ward-host)). DEPLOYMENT.md's table is the full list.

`config.ts` is a pure function of an environment *bag* and touches `process` nowhere, because a Worker has no ambient environment — its vars and secrets arrive as an argument on every request. Each entry point loads the config once and installs it in a module-wide live binding.

**What the app supplies for itself** (`identity.ts`), so that a Deploy-to-Cloudflare button needs nothing but a password and a name. After the schema is up, `loadStoredIdentity()` fills whatever the environment left unset from `settings`: a VAPID pair, generated on first boot and minted insert-if-absent as **one** JSON value (two isolates racing must agree on a pair, not each win half), and a public origin. The origin is learned by `learnOrigin()` on `GET /admin` — a signed-in **admin** request only, its own URL only (no forwarded headers), https only — because it becomes the address in every notification and share link and must not be settable by a stranger's `Host` header. First one wins. The send path re-reads it if its isolate booted before another learned it, and an empty `VAPID_SUBJECT` falls back to it; with neither, a drain leaves the queue unclaimed rather than spend attempts. Values in the environment always win, so an existing deployment is never re-keyed. Node keeps `PUBLIC_ORIGIN` required in production: behind a TLS-terminating proxy it never sees an https origin to learn.

`assertConfig()` throws on anything missing or malformed, and **warns** (never fails) when `ADMIN_PASSWORD` is shorter than 12 characters. A warning rather than a rule because refusing to boot would lock a ward's only admin out of their own dashboard over a policy — but it is worth saying, since that password is also what derives the admin session's signing key.

The public app shell (`public/index.html`) is served dynamically by the server with `{{APP_NAME}}` / `{{APP_SHORT_NAME}}` / `{{APP_DESCRIPTION}}` placeholders substituted at boot (and `APP_NAME` published to client scripts via `<html data-app-name>`); the manifest is rendered from the same config. `shell.ts` does that substitution for both runtimes — only *reading* the files differs (disk on Node, the assets binding on Workers).

## Security notes for reviewers

Risks that are known and accepted, so a review or a report can start past them. Each was checked against the code it names.

- **Rate limits are per isolate on Workers** (`ratelimit.ts` counts in memory): a speed bump against guessing, not a global budget. See [Three entry points, one app](#three-entry-points-one-app).
- **`WARD_OWNER_SIGNIN=on` multiplies the password oracle by the number of wards.** Each hosted ward builds its own app and so its own limiters, and with the switch on every ward's `/admin/login` takes the platform password. Keep it off in production; only the test configs set it.
- **An installed app's device token travels in `?code=` on a cold launch** (`start_url`; see [Rotation](#rotation)), so it lands in a reverse proxy's or Cloudflare's request logs. The app's own log lines redact it (`redactUrl` in `log.ts`). It is a per-device token, not the shared code, and Issue a New Code's *Everyone, including installed apps* cancels it.
- **Editors can obtain the member code**: they hand out the share link, the QR and the flyer, and mint emailed links. Removing a person does not change the code; issue a new one (with no grace) after removing someone who should no longer have it.
- **Signing out *Everyone who used a browser* leaves device tokens, invites and emailed links in place**, so installed apps let themselves back in; *Everyone, including installed apps* is the hard stop. Neither touches push subscriptions: a phone keeps receiving the notifications' text until it is removed under Subscribers.
- **Announcement and page images are public to anyone with the URL**: a 128-bit random key, served ungated with a one-year `immutable` cache, so a copy fetched before a delete can outlive it. Program images are not (see [Image attachments](#image-attachments)).
- **The many-ward host's operator is fully trusted.** The operator's export carries everything — the people-session key (`admin_people_secret`) in the clear, the VAPID private key sealed under the host's `BACKUP_SEAL_KEY`, which the operator holds, or in the clear on a host that sets no such key — and the operator can mint an admin invite into any ward.
- **A backup's push keys are only as secret as `BACKUP_SEAL_KEY`.** The dashboard's backup and the operator's export carry the VAPID pair sealed under one deployment-wide key (`seal.ts`): whoever has both a file and that secret can push to every member in it. The key lives with the other secrets and is never written to the database or a file; with no key set, the pair is left out of the dashboard's backup altogether (the operator's export, above, carries it in the clear instead).
- **Retired access codes are never purged.** A retired code stays in the table after its grace runs out (it no longer opens anything). Expired invite, email and device tokens are deleted a month after they lapse, and the send history a year after each send (`maybePurgeHistory` in `tick.ts`).
- **Backups keep programs beyond the retention window.** The clock deletes programs from the database, not from a ZIP an admin downloaded last spring.
- **HSTS is not the app's job.** It sends no `Strict-Transport-Security` header: on Node the reverse proxy should, and on Workers it is a setting of the Cloudflare zone.
- **The operator's API bearer token is the platform password itself**, sent with every scripted call. The session cookie no longer leaks it (its key mixes in a secret the registry holds, `sessionKey` in `operator.ts`), but a script's environment or shell history still can.
- **A ward created, moved or deleted can answer wrongly for up to a minute** on isolates that looked its hostname up before: `lookupWard` in `host.ts` caches each answer, a "no such ward" included, for 60 s per isolate.
- **One alarm drains a hosted ward's whole queue** (`runTick(…, 'all')` → `drainSendQueueUntilEmpty`), one push-service fetch per subscriber, so past roughly 900 subscribers a single Durable Object invocation could reach Cloudflare's subrequest cap (1,000 per invocation on the paid plan when this was written; check the current figure). Wards are a few hundred people.
- **Two concurrent redemptions of one dashboard invite can both register a passkey.** `redeemAdminInvite` in `db.ts` checks the invite, then marks it used and inserts the passkey in one batch, but the insert does not depend on the mark having changed a row. Both requests need the link, whose holder could register anyway.
- **`public/zip.js` inflates each entry fully before checking its size**, so a crafted backup ZIP can exhaust the memory of the browser restoring it. Only an admin's dashboard and the operator's page open one, with a file they chose.
- **Member pages render every published Markdown body on every request**, uncached (`/api/announcements`, `/api/pages`, `/api/program`). Several bodies at the 50,000-character cap could exceed a free-plan Worker's CPU budget.
- **The `?msg=` flash on dashboard pages is attacker-choosable.** It is escaped, but a crafted link shows its text styled as a success message to a signed-in admin.
- **An image keeps its EXIF Orientation and its colour profile, nothing else.** Every byte that enters the store is passed through `image-meta.ts` first (the upload route, the host's Import Backup, `scripts/db-restore.mjs`), which drops GPS, capture time, device, thumbnail, XMP, IPTC and comments from a JPEG, PNG, WebP or GIF without decoding it, and rewrites the Orientation into a minimal Exif block so a phone photo still displays the right way up. A file whose structure it does not understand is stored as sent — the stripper never refuses an upload — so a crafted file could carry metadata through. So can a real photo whose name does not match its format (a JPEG saved as `.png`), since the format is taken from the declared type rather than sniffed, and a JPEG's trailing data after its image (an HDR gain map, which can hold its own XMP) is kept as it is.
- **The announcements PDF has no CJK or Thai glyphs.** It is set in pdfmake's Roboto plus Noto Emoji (`public/preview-pdf.js`), with no fallback, so that text does not print.
- **Editor drafts outlive a session that merely expires, and a crafted link can discard them.** `editor/drafts.js` keeps unsaved edits in `localStorage` (a program's names included) until they are saved, until that editor is next opened more than 14 days later, or until Log Out, whose landing page (`/admin/login?out=1`) clears every draft on the device. A session that expires leaves them, on purpose, to be offered back after signing in — so a device nobody logged out of keeps them; and because the flag is a query parameter, a link to `/admin/login?out=1` that an admin opens discards their unsaved drafts (a nuisance, not a disclosure).
- **New announcements default to Published**, and **a program left on screen stays there after its window closes** until the next focus or visibility change refetches it (the service worker's offline copy is the one that honours `closesAt`). Both deliberate for now.

## Tests

`npm test` builds and runs the suite against the Node entry on a throwaway SQLite file; `npm run test:worker` runs the same access-gate, attachment, program, hardening, role, passkey and ward-settings suites against `wrangler dev` — the real Workers runtime, on a fresh local D1 per run (no Cloudflare account needed), first with the template config (images in D1) and then the attachment suite again with a simulated local R2 bucket bound (`test/wrangler.r2.jsonc`) — so a divergence between the runtimes fails a test rather than a Sunday. `npm run test:host` runs those suites again against the many-ward host (`test/wrangler.host.jsonc`, and attachments once more with R2), then `test/host/`. `test/helpers/harness.js` is the only file that knows which target is running. It gives each `wrangler dev` an `--inspector-port` of its own: they all default to 9229, so the moment a fifth or sixth server exists somewhere in the suite the extra one dies with `Address already in use` and every test in its file reports `worker server exited before serving` — a failure that names the wrong culprit entirely. Note also that a per-test rate-limit bucket cannot be bought with an `X-Forwarded-For` header on both runtimes: `clientIp` prefers `cf-connecting-ip`, which the Workers runtime sets itself, so a trick like that passes on Node and 429s under wrangler. `test/push-queue.test.js` is Node-only by construction: it drives `sendToAll()` in process, over the real schema and real encryption, with a stub over `globalThis.fetch` playing the push service. It also pins the states no HTTP route can produce — a claim that never commits, a lease wound past its expiry, a `pending` batch with an empty queue — by reaching into the SQLite file through a second driver handle, because a crash is not something an API can be asked for politely. Its coverage tests own both kinds of skip too: that a Sunday with nothing posted queues nothing and logs why, that a date in `send_skips` suppresses a send even with announcements up and logs the admin's own words, that the decision sticks so a 2pm publish cannot fire the digest off-schedule, that *removing* a skip afterwards cannot resurrect the send, that a skip is never pruned on its own day, and that the following Sunday is unaffected.

`test/sw-notificationclick.test.js` is the odd one out: it evaluates **`public/sw.js` verbatim** in a `vm` context with the worker globals stubbed, because a service worker cannot be imported and `npm test` has no runtime to host one. Only the environment is fake — the branching under test is the real file. It exists because the handler's matching is exactly the kind of thing that looks harmless and silently breaks the feature: matching an open window by **pathname alone** would leave a member parked on `/#program` with that window merely focused, reading the program under a notification about the announcements. The suite asserts the routing for each open-window state (on the program tab, on a bare `/`, already on the target, an admin tab, nothing open, a custom external link), that every reused window is told to refetch, and that the refresh message is posted **before** `focus()` — the ordering that forces `refreshOnResume({ force: true })` to skip the visibility guard as well as the throttle.

`test/gate-unlock.test.js` does the same trick for the gate page's **inline** unlock script, extracted from `gatePage()`'s rendered HTML and evaluated in a `vm` with `location`, `fetch` and a two-element `document` stubbed. The case it exists for is a same-document arrival: a member sitting on the gate who opens their `#code=` link *in that same tab* changes only the fragment, so nothing reloads and a one-shot script would never run again. It asserts the exchange happens both at load and on a later `hashchange`, for `#code=` and `#i=` alike, that the credential is URL-decoded, that a hash change mid-request does not double-post, that a rejected code leaves the page able to accept the next link rather than wedged shut, and that unlocking at a path beginning `//` stays on this site. `test/hardening.test.js` covers the composed security behaviours that no single module owns: the `nosniff` and `private, no-cache` headers on both public APIs, `private, no-store` on every admin page, a non-date expiry being refused and escaped where it is echoed, a rejected save handing back the submitted text, the `?code=` redirect refusing to leave the origin, non-string credentials being rejected rather than 500-ing, `/administrivia` being gated (i.e. the admin exemption is not a prefix match), the per-device invite cap (including that a `?code=` credential is no way around it), the length caps on every kind of content, a backup being no way into the dashboard, a *correctly signed* member cookie with an ancient `issuedAt` being rejected — it reads the signing key out of `/admin/backup.json` so the forgery is genuine, and pairs it with a fresh-timestamp control — and a program's `/images/<key>` URLs appearing in **no** unauthenticated response while its window is shut. `test/roles.test.js` covers the admin/editor split from both sides: what an editor may do (write an announcement that reaches members, write a program and preview it outside its window, write, reorder and delete a resource page — with an unpublished one staying off `/api/pages` — render a preview, hand out the share link and QR), what an editor may not (every `requireAdmin` route, asserted as a 403 over HTTP — the guard, not the hidden button — plus the same admin session reaching each of them, so a 403 means "wrong role" rather than "broken route"), that the dashboard renders exactly that split, and that the content policy is on both roles' dashboards. Its shape is dictated by one thing worth remembering when adding to it: `/admin/login` allows five attempts a minute per IP, and the whole file shares one client, so both sessions are established once in the top-level `before` and the two deliberate failures are counted. `test/programs-core.test.js` is Node-only for the same kind of reason: the dot-leader rule and the window arithmetic are functions of their inputs and are best pinned to specific instants (07:59 on the day, either side of a DST change) rather than run against whatever the clock says, and the retention purge has no route at all — it is driven by a cron tick, so the only honest way to test it is to call it with a `FileStore` that records what it was asked to delete.
